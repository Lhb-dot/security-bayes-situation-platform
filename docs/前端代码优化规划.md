# 前端代码优化规划

日期：2026-10-10。基线：`5332450`，四场景管理员首页已恢复新版；规划时工作区干净，`npm run build` 已通过。

## 范围与实施原则

本轮优化前端内部实现，保持现有页面样式、文案、布局、导航、业务流程和接口协议。纯重构与缺陷修复分别提交：纯重构要求行为一致；缺陷修复只调整异常、并发或失效会话下的错误行为。

先抽取脚本逻辑，保留页面模板和样式。暂不拆分带 scoped 样式的视觉组件，避免选择器作用域和 DOM 层级变化。按任务逐项提交，每项都可单独回退，不一次替换整个历史目录。

## 已核实的现状

- 当前源码约 2.4 万行，7 个 Vue 页面超过 1,000 行。RiskInference、ModelCenter、ReportCenter 分别约 1,736、1,629、1,475 行（含模板、样式、注释）。
- request.js 与 trainingApi.js 仍是 JavaScript；TS 开启 strict，但请求返回值缺少完整类型约束，模型评价接口存在 Record<string, any>。
- 三个后台任务 Store 各自实现定时器、防重入、超时、已读、终态裁剪与过期清理，存在重复代码。
- 时间处理分散：报告与批量任务处理 Unix 秒，训练处理北京时间无时区字符串，推理记录处理 UTC 字符串。必须保留不同来源的语义，不能一律补同一种时区。
- 模型中心列表已有请求序号保护，报告详情已有令牌保护；风险研判的级联加载、样本分页和报告列表尚无同等保护，需以延迟响应验证竞态。
- 请求层设置 timeout: 0，应用在 bootstrap 完成后才挂载。会话请求悬而未决时，存在启动长期等待风险。
- AI 解释和模型评价各实现一套相似的 SSE 读取与解析逻辑。
- 当前 package.json 没有 test/lint 脚本；已有浏览器验证脚本的 hash 路由描述与当前 history 路由不一致，不能直接视为有效回归保障。

## 实施顺序

| 阶段 | 内容与主要范围 | 验收与提交边界 |
| --- | --- | --- |
| 1. 建立回归基线 | 核对并恢复合适的历史测试配置；记录三种角色、四场景首页和关键业务流程；校正浏览器验证脚本的路由方式。 | 类型检查、构建、复用的有效测试通过；记录验证方式。不为了增加覆盖率编写实现镜像测试。 |
| 2. 统一基础工具 | 优先处理日期解析、已用时间、错误消息、终态裁剪等有明确重复的函数。 | 分别验证 Unix 秒、带时区 ISO、北京时间和 UTC 无时区字符串；保持现有展示格式和任务计时。时间与任务辅助函数分开提交。 |
| 3. 补齐 API 类型 | request.js → request.ts；trainingApi.js → trainingApi.ts；核对模型评价事件类型。 | 显式区分接口原始对象与前端对象；保持导出函数和调用方式；采用与现有 Axios 拦截器行为一致的响应类型，避免用 any 隐藏错误。每个 API 模块独立提交。 |
| 4. 收敛轮询重复 | 核对历史 jobPollingCore；保留三个业务 Store，只共享定时、防重入、停止/重启和失效响应保护。依次接入训练、批量推理、报告。 | 验证重复启动、慢请求、换账号/登出后旧响应、刷新恢复、完成只通知一次。训练终态、报告下载、批量结果各保留独立业务逻辑；三个 Store 分别提交。 |
| 5. 修复请求竞态与等待风险 | 风险研判的场景→数据集→模型→字段→样本加载；报告列表分页；datasetStore 共享状态；会话恢复和普通查询超时。 | 延迟响应倒序返回时只采纳当前选择；旧请求不覆盖 loading/error；失败与取消不冒充空数据。按接口分类设置等待策略，长任务提交、上传和 AI 流不能一刀切。缺陷修复独立于重构提交。 |
| 6. 统一 AI 流式读取 | 抽取两套 SSE 的传输和解析部分，业务事件由各接口自行适配。 | 验证分块 UTF-8、跨块事件、CRLF、多行 data、错误、取消、正常结束和 reader 清理；统一流式请求的会话失效处理。保持现有 AI 面板和输出内容。 |
| 7. 按业务拆脚本 | 从 RiskInference 的级联选择与样本加载开始；再处理 ModelCenter 的列表/筛选与 AI 评价；最后处理 ReportCenter 的列表、生成操作和详情数据转换。 | 抽为按业务命名的 composable 或纯函数，页面保留模板和 style；不以行数为唯一目标。每个业务模块独立提交并验证事件、watch 和卸载清理。 |

## 第一批建议交付

先完成阶段 1～3：复用有效回归检查、统一基础工具、补齐 request 和 trainingApi 类型。它们边界明确，也为后续轮询和异步请求改动提供基础。之后完成阶段 4～6，最后拆大页面。

不提前承诺性能提升百分比。包体优化暂后置，先测量报告中心大 chunk 的依赖组成，再决定是否需要调整加载边界；不因构建告警直接改分包配置。

## 验证要求

每项完成后运行类型检查与构建，以及该项相关的有效测试。涉及运行时行为的改动，要验证对应真实页面，不只依赖编译通过。

重点场景：三种角色的落地与退出；刷新和直接进入业务地址；快速切筛选与分页；训练/批量/报告在切页及刷新后的恢复；任务结束时通知及下载；账号切换后状态清理；AI 开始、停止、切模型与离开页面；异常网络下的等待与恢复。

拆分逻辑时以相同账号、数据和视口核对关键页面截图，页面布局和样式保持一致。构建产物和临时验证文件不纳入源码提交。

## 当前不开展的工作

不改首页设计、不调整 CSS 或主题、不换框架/组件库、不全仓格式化、不机械清除全部类型断言、不删除未经核实的接口、不改变后端协议或数据库，也不把所有状态管理重写成通用框架。

本文件仅是实施规划，创建时未修改前端源码、依赖或业务行为。
