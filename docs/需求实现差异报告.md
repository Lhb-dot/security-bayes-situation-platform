## 二、P0 关键缺口

### 2.1 模型生命周期：无独立 `ENABLED` 状态（需求 6.7.2）

需求规定状态机必须为 `TRAINING → FAILED/DRAFT → PUBLISHED → ENABLED → DISABLED`，其中「发布」与「启用」是两个独立动作：训练发起人发布为 `PUBLISHED`（待启用），再有管理级账号显式启用为 `ENABLED` 才可供场景用户推理。

**当前实现：**
- 状态集仅 `TRAINING / FAILED / DRAFT / PUBLISHED / OFFLINE / DISABLED`（`backend/app/services/constants.py:180-185`）。
- 状态转换表 `MODEL_STATUS_TRANSITIONS` 为 `DRAFT→PUBLISHED/DISABLED`、`PUBLISHED→DISABLED`、`DISABLED→PUBLISHED`（`constants.py:200-207`）。
- `enable` 接口实际只是把 `DISABLED → PUBLISHED`（`model_version_service.py:437-447`），没有独立的 `ENABLED` 档位。

**影响：** 需求附录 D 明确将此列为正式需求调整；当前「PUBLISHED」同时承担「已发布」和「已启用可推理」两种含义，与需求的发布/启用分离不符，属于核心生命周期偏差。

### 2.2 批量推理缺失（需求 6.9）

需求要求：除单条手动输入外，支持上传 CSV/JSON 文件批量导入待测样本执行批量推理（字段校验、逐行错误定位、批量结果独立展示）；**航母甲板作业场景（278 个输入特征）的文件导入推理为 P0 必需**。

**当前实现：** 后端仅 `POST /inference-records/predict` 单条推理（`inference_record_routes.py:23-48`）；前端仅 `predictInference` 单条表单（`RiskInference.vue`）。全站无 batch/批量/文件导入推理实现；唯一 CSV 导入是训练数据集上传（`/datasets/upload`），与推理无关。

**影响：** 航母场景因特征过多无法手动填写，其推理能力实质不可用——这是 P0 业务闭环缺口。

### 2.3 航母甲板热点图未实现（需求 7.4.1）

需求要求：航母场景生成 `RiskEvent` 时额外存储 `fault_position_x/y`，前端在甲板底图上叠加红色圆点定位碰撞位置。

**当前实现：**
- `fault_position_x/y` 仅作为类型字段存在（`frontend/src/types/security.ts:168-171`），事件详情页以纯文本展示（`RiskEventDetailView.vue:165-166`）。
- 后端坐标生成是**占位启发式**（`risk_event_service.py:121` 注释「计算逻辑（占位，待与业务方确认正式映射）」）。
- 前端看板散点图用「双机平均航向角映射」的占位坐标（`DashScatter.vue:4` 注释），无甲板底图、无热点图网格。

**影响：** 需求 7.4.1 的核心可视化（红点定位）未落地。

## 三、功能缺口（部分实现）

### 3.1 处置动作 `ASSIGN` 未实现（需求 5.2.2）

需求规定处置动作含分派（ASSIGN）、变更状态（UPDATE_STATUS）、追加说明（ADD_COMMENT）三类，且每次操作生成处置记录。

**当前实现：**
- `HandlingRecord` 模型与 `HandlingRecordService` 存在；`PUT /risk-events/{id}/handle`（→ UPDATE_STATUS）与 `POST /risk-events/{id}/comment`（→ ADD_COMMENT）已实现。
- 但 `ASSIGN` 仅在 `constants.py:309` 定义了常量，**没有任何接口或服务路径写入它**（全局检索仅命中常量定义与 docstring）。

### 3.2 ~~三个场景字段目录缺失~~ ✅ 已解决（作者 0171923）

> **已解决：** 作者已提交完整 `scenario_feature_catalog.py`（`_power_catalog`/`_geological_catalog`/`_carrier_catalog` 三个目录生成器），经 `validate_explanation_config.py` 验证输出 8/51/280/80 全部通过。以下为原差距描述，保留备查。

需求要求：风险事件详情/报告的解释文本须「结合场景特征生成」，即每个场景要有完整的 `feature_dictionary`（中文名、含义、高/低/异常值说明、处置措施）。

**当前实现：** `scenario_configs.json` 中仅 `network_security`（80 字段）完整；`power_system`(8)、`geological_risk`(51)、`flightdeck_operation`(280) 的 `feature_dictionary` 为空。生成这些字段族的模块 `backend/app/data/scenario_feature_catalog.py` 从未提交（被 `.gitignore` 的 `data/` 规则静默吞掉）。

**影响：** 这三个场景的特征解释与报告特征说明走 `get_scenario_config` 的降级兜底文案，无法按需求给出「受影响设备/滑坡关键因子/最小间距」等场景化解释。

### 3.3 报告解释输出部分算法缺失 + 条件密度未实现（需求 6.6.2 第 6 条 / 6.10）

需求要求算法接口输出：最终预测及类别概率、不同视图预测与概率、视图权重、各特征的实际取值/所属视图/特征权重/按类别条件概率（**连续特征为条件密度**）/加权贡献值，以及 `calculation_method`。

**当前实现（`NbAlgorithmService.java` / `PredictServer.java`）：**
- 已输出：`prediction_label`、`class_distribution`、`views`、`view_weights`、`feature_evidence`（含 `weight`/`cond_prob`/`contribution`）、`calculation_method`。
- **缺失：**
  - `A2WNB` 完全无 `views`/`view_weights`/`feature_evidence`/`calculation_method`（`NbAlgorithmService.java:307-339`）。
  - `DIWNB` 无 `feature_evidence`/`calculation_method`（`:269-306`）。
  - 多视图算法（MAWNB/EMAWNB/PMWNB）的 `feature_evidence` 只覆盖「原始属性视图」，其余视图无逐特征证据。
  - **连续特征「条件密度」未实现**：训练时所有连续特征被 `FilteredClassifierWithDiscretize` 离散化（`NbAlgorithmService.java:763-778`），输出的是离散条件概率而非条件密度。
