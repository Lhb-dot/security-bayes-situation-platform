## 2. 死代码判定

### 2.1 `model_sim.py`：**不是零引用死模块，是「可达但无人走」的遗留簇**（不改，列提案）

**任务书假设「零引用 ⇒ 报告并建议删除」，实测不成立。** 证据（全仓 grep，排除 `node_modules`/`dist`/`.git`）：

```
=== A. model_sim 引用（全仓，排除自身） ===
backend\app\api\legacy_model_routes.py:19: from app.services.model_sim import get_dataset_list, infer_bayes_sim, train_bayes_sim
=== B. legacy_model_routes 引用 ===
backend\app\main.py:18: from app.api.legacy_model_routes import router as legacy_model_router
backend\app\main.py:138: app.include_router(legacy_model_router)
=== C. check_service_health / execute_pmwnb_predict ===
backend\app\services\model_sim.py:172: def check_service_health() -> bool:
```

**调用链完整、路由真的挂载了**：`main.py:138` → `legacy_model_routes.py` → `model_sim.py`，端点 `/api/model/dataset-list`、`/api/model/train`、`/api/model/infer` 在运行中的服务上是**可访问的**（本分区未启服务实测，仅静态确认 `include_router` 未被条件包裹）。

**但它已经没有任何真实使用者**：

```
=== E. 前端是否调用 legacy /api/model/* ===
（空）
```

`frontend/src` 全仓 grep `/api/model/`、`dataset-list`、`save-threshold`、`exp-records`、`risk_statistics` → **0 命中**；`backend/tests/**` 也无引用。即：**后端仍挂着一条前端从不调用、测试从不覆盖的旧链路**。

**是否被 Java 算法服务取代：是。** 取代关系如下：

| 能力 | 旧路径（`model_sim.py`） | 新路径（现行） |
|---|---|---|
| 训练 | `train_bayes_sim` → `PMWNB_SERVICE_URL/train` | `training_executor.execute_algorithm_training` → 同端口 12313，**并覆盖 A2WNB/MAWNB/EMAWNB/CAVWNB/DIWNB（12315）** |
| 预测 | `infer_bayes_sim` → 手工解析响应 + **用进程内 `global_threshold` 分档** | `training_executor.execute_algorithm_predict`（PMWNB 走 12314）→ `inference_record_service._predict`，阈值改为 **DB 阈值配置 + 按查看者重算**（`risk_view`） |
| 数据集清单 | `get_dataset_list`（3 个硬编码 CSV） | `dataset_service` 的 `datasets` 表（当前 19 条） |
| 模型产物 | 模块级 `os.makedirs(TRAINED_MODEL_DIR)` | `training_executor.build_model_save_path` |

## 3. `training_runner.py` vs `training_executor.py`：职责不同、都不是死代码

**任务书怀疑两者重复或其一为纯转发。实测结论：两者是「调度」与「执行」的分层，无重复、无纯转发。**

| 维度 | `training_runner.py`（205 行） | `training_executor.py`（161 行） |
|---|---|---|
| 定位 | **进程内任务调度器**：守护线程 + `queue.Queue` + 兜底回收 | **无状态 HTTP 客户端**：对接 Java 算法服务 |
| 有无状态 | 有（`_queue`/`_stop`/`_lock`/`_threads`/`_started` 5 个模块级可变对象） | **无**（纯函数，除 `os.makedirs` 无副作用） |
| 是否碰 DB | 是（`SessionLocal`，`model_versions.status` 生命周期） | 否 |
| 是否碰 HTTP | 否 | 是（`requests.post`，timeout 600/60） |
| 并发模型 | 1..4 个 worker 线程 + 队列 | 同步阻塞，由调用方线程承担 |
| 环境变量 | `TRAINING_RUNNER_ENABLED` / `_WORKERS` / `TRAINING_STALE_MINUTES` | 无（配置来自 `algorithm_config`） |
| 启动点 | `main.py:141` | 无（被 import 即用） |

**真实调用关系（三段式，已逐行核对）**：

```
main.py:141 _start_training_runner() → training_runner.start()
    ↓ (queue)
training_runner._worker → _execute(model_id)
    ↓
model_version_service.run_training_job(model)        # 453 行，不抛异常，失败落状态
    ↓
model_version_service._run_algorithm_training(...)   # 475 行，解析路径 + 取 risk_labels
    ↓
training_executor.execute_algorithm_training(...)    # 84 行 → _request_train → Java
```

**「是否纯转发」逐函数核对**：`training_executor` 的 7 个函数**没有一个是纯转发**：
- `resolve_dataset_path` / `build_model_save_path` 有实际路径计算；
- `_request_train` / `_request_predict` 有请求组装 + 20 字段规整 + 错误语义翻译；
- `execute_algorithm_training` / `execute_algorithm_predict` 有分派（PMWNB 专用端口 vs 通用端口）+ 未配置校验；
- `execute_pmwnb_training` 是**唯一的薄封装**，但它承载「PMWNB 走 12313、其余走 `ALGORITHM_SERVICE_URLS`」这条分支，且被 `execute_algorithm_training` 调用 → **保留**（本次仅删掉其内部恒真赋值）。

**`training_runner` 是否有死函数**：`stop()` 零引用（保留，见 §2.2）；其余 9 个函数均有调用方。

**结论**：两个文件**都是活的、都不重复**，无需合并也无需删除。合并反而会把「HTTP 客户端」和「线程调度」耦合在一起，并使 `inference_record_service._predict`（只用 executor、不用 runner）被迫依赖线程模块。

## 5. 正确性核查

### 5.1 【已修】`_run_batch` 的进度回调漏报失败条

- **位置**：`inference_record_service._run_batch` 原 L462-529
- **现象**：失败分支在 `items.append(...)` 后 `continue`，**跳过了 `on_progress(index + 1, …)`**。若末尾连续 N 条失败，前端进度条会**永远停在最后一个成功条数**，直到任务整体结束才跳到 `processed=total`。对「200 条里最后 50 条全失败」的批次，用户会看到进度卡在 75% 长达数分钟。
- **修法**：把失败分支改成 `if/else` 结构，回调移到分支之外，**每条都汇报**。
- **兼容性**：`test_batch_inference_async.py:107` 断言全成功时序列为 `[1, 2]` —— 修改后全成功路径的调用次数与参数**完全不变**（仍是 `1,2`），失败路径从「漏报」变为「补报」。**该测试仍通过。**
- **未改的部分**：`on_progress` 的签名、`succeeded/failed/risk_count` 的累计语义、`items` 结构与顺序均未动。

### 5.2 【已修】`batch_inference_runner` 的任务字段无锁写入 → 半更新快照

- **位置**：`batch_inference_runner._execute`（原 L204-260）
- **现象**：`_jobs_lock` 保护了 `_jobs` **字典结构**，但 `_execute`/`on_progress` 对 `BatchJob` **字段**（`status`/`processed`/`succeeded`/`failed`/`risk_count`/`items`/`error`/`finished_at`/`samples`）的写入**完全在锁外**，而读侧 `get_job`/`list_jobs` 是**持锁**遍历这些字段的。结果是：轮询接口可能读到「`status=DONE` 但 `processed` 仍是上一轮值」「`succeeded` 已更新而 `failed` 未更新」这类**半更新快照**；`to_dict()` 里 `result` 块的 5 个字段也可能互相不一致。
- **为什么现在才暴露**：GIL 保证**单次属性读/写**原子，所以不会读到「半个整数」，但**多字段之间**没有一致性保证。前端每 2 秒轮询一次，撞上不一致窗口的概率不低（一次 `_update_job` 写 6 个字段，与读并发）。
- **修法**：新增 `_update_job(job, **fields)`，在 `_jobs_lock` 内批量赋值；`_execute` 的**全部** 9 处字段写入都改走它。
- **死锁核查**：`_jobs_lock = threading.Lock()`（**非可重入**，L45）。已逐一确认 `_update_job` **从不在持锁上下文中被调用**：`create_job` 在锁内只调 `_purge_locked`（不调 `_update_job`）；`_loop`/`_execute` 均在锁外调用。**无死锁。**
- **性能影响**：锁只覆盖「几次 `setattr`」（纳秒级），不覆盖逐条研判（秒级），因此**不阻塞进度查询**。
- **兼容性**：`test_batch_inference_async.py` 直接读 `batch_inference_runner._jobs[job_id].samples`（L248）、直接改 `_jobs[live_id].created_at`（L291）—— 测试的**直接字段访问**不受影响；`get_job`/`list_jobs` 返回结构不变。

### 5.3 【已修】`_validate_dataset_file` 三处近重复分支（§2.2 #5）

行为等价论证见 §2.2。额外核查：`expect` 可能为 `None`（老数据 `fields_schema` 缺 `type`）时，原写法三分支都不命中、新写法也不命中 ⇒ **同样落到 `return None`（放行）**。**行为完全一致。**

### 5.7 【未修·报告】`training_runner.reap_stale` 会把「还在排队」的任务误判为中断

- **位置**：`training_runner.reap_stale` L98-106
- **机制**：判据是 `status == TRAINING AND trained_at < now - 60min`。而 `trained_at` 是**建版本时间**（`model_version_service.create` L318 `trained_at=now`，字段 `nullable=False`，见 `models/model_version.py:54`）——**不是「开始执行时间」**。`model_versions` 表**没有 started_at 字段**（`model_version_service.py:404` 的注释也明确写了「model_version 没有完成时间字段」）。
- **后果**：`DEFAULT_WORKERS=1`、单次训练最坏 600 秒 ⇒ **队列里积压 > 6 个任务时，最后一个还没开始跑就会被标记 FAILED「训练任务中断」**。前端显示「训练失败：训练任务中断（服务重启或执行器停止），未能完成」，而实际上它只是还没轮到。`_execute` 随后会因「状态非 TRAINING」而跳过（L75-79），任务被静默丢弃。
- **触发条件**：需要同时满足「并发提交 ≥7 个训练」+「单个耗时 ≥10 分钟」，属**低频但可复现**。
- **为何未修**：正确修法是引入 `started_at`（**新增 DB 字段 → 协议禁止本分区改 `models/**`**）或把兜底判据改为「队列中不存在该 id 且状态仍 TRAINING」（需要 runner 暴露 `_queue` 快照，且跨进程重启场景会失效）。**两者都超出本分区权限/风险预算**，列 §9 B3-P3。
- **已确认不存在的同类问题**：`trained_at` **不是** NULL（`nullable=False` + 建版本时必写），所以 `trained_at < cutoff` **不会**因 NULL 比较而恒假 —— 该函数**确实在工作**，不是死分支。

### 5.8 【未修·报告】`batch_inference_runner` 的两处边界

1. **`create_job` 无背压**：`_purge_locked` 只清**终态**任务（`TERMINAL_STATUSES`），进行中的任务永不淘汰；`_max_jobs()` 的溢出裁剪也只从终态里挑（L184-189）。因此 100 个并发提交可让内存里同时挂 100 个 `BatchJob`，每个持 200 条样本 dict ⇒ **最坏 2 万条样本常驻**。无拒绝逻辑（不返回 429/503）。
2. **`SessionLocal()` 抛异常则任务永久 RUNNING**：`db = SessionLocal()`（L225）在 `try` **之外**，若它抛异常（DB 连接池耗尽），异常会冒到 `_loop` 的 `except Exception`（L271）被记录，**但 `_execute` 内既没写 FAILED、也没写 `finished_at`**（`finally` 属于后面那个 `try`，此时尚未进入）⇒ 任务**永久停在 PENDING→RUNNING 之间**（实际是 PENDING，因为 `_update_job(status=RUNNING)` 在 L214 已经执行）→ **永不进入终态 ⇒ 永不被 `_purge_locked` 清理**，前端轮询永远转圈。修法：把 `SessionLocal()` 移入 `try` 或用 `contextlib.closing`。**本次未改**（需要重构 `_execute` 的异常边界，收益/风险比不划算，且现有测试覆盖不到该路径）。
