### 安全专项结论（本分区 P0 三问）

#### ① 会话/令牌模型（`models/auth_session.py` + `schemas/auth.py`）

**结论：设计正确，无明文令牌，无泄漏，索引完备；缺口只有"过期行不清理"。**

- **过期字段**：有 `expires_at`（NOT NULL），并在 `api/deps.py:56-61` 强制校验（`session.expires_at <= now` → 401）。
- **撤销机制**：有 `revoked_at`（nullable）。置位点两处：登出 `api/v1/endpoints/auth_routes.py:92`；改密后批量撤销该账号全部活跃会话 `services/user_service.py:286-291`（`UPDATE auth_session SET revoked_at=now WHERE user_id=:id AND revoked_at IS NULL`）。校验点在 `deps.py:58`。
- **明文令牌落库**：**没有**。库中只存 `digest_token(token) = HMAC-SHA256(AUTH_SESSION_PEPPER, token).hexdigest()`（`utils/auth.py:51-52`），64 字符，列宽 `String(128)` 足够；明文令牌只出现在 `Set-Cookie` 与登录响应体里（后者见下）。pepper 强制 ≥32 字符（`utils/auth.py:10-14`，缺失直接 `RuntimeError`，不会静默降级成无 pepper 哈希）。
- **索引**：`token_digest` 上的 `unique=True`（对应迁移 `20260820_000001:38` 的 `sa.UniqueConstraint`，PG 会自动建唯一索引）⇒ 令牌校验是**索引点查，不会全表扫**。另有 `ix_auth_session_user_id`（批量撤销用）、`ix_auth_session_expires_at`（目前**无查询使用**，为清理任务预留）。
- **Cookie 属性**：session cookie `HttpOnly=True`；csrf cookie `HttpOnly=False`（双提交模式必需）；`Secure` 默认 `true`（`AUTH_COOKIE_SECURE` 可显式关，供本地 HTTP）；`SameSite` 默认 `lax`；`path="/"`。CSRF 校验用 `hmac.compare_digest` 常量时间比较，且要求 cookie 与 header 双匹配，只对 `POST/PUT/PATCH/DELETE` 生效（`deps.py:63-75`）。
- **缺口（报告，不修）**：
  1. 无过期/撤销行清理任务 ⇒ 表单调增长（D6）。
  2. 无并发会话数上限、登录不轮换/不踢旧会话 ⇒ 同一账号可无限累积活跃会话（改密能一次性清掉）。
  3. `expires_at` 是**绝对过期**，`last_seen_at` 只用于展示节流写入（`deps.py:22-25,77-87`），**不续期** ⇒ 默认 8h（`utils/auth.py:7`）后必须重新登录。属设计选择，非缺陷。
  4. `AuthSession.user` relationship 零引用（B 项）。

**`schemas/auth.py` 是否会把口令哈希或内部 token 回传前端？**
- `AuthResponse` 里**没有** token 字段，也不含 `password_hash` ⇒ 即使被使用也不会泄漏。
- 但**登录响应根本不是用它序列化的**：`auth_routes.login` 声明 `response_model=ResponseModel`（`data: Any`），手写 dict 返回。实际响应结构为
  `data = { user: row_to_dict(AppUser, exclude=("password_hash",)) + scenario_code, expires_in, csrf_token }`。
  即 `AuthUser` 的字段集与真实响应**恰好吻合**（`created_at/updated_at` 也是字符串，因为 `row_to_dict` 会格式化成 `"YYYY-MM-DD HH:MM:SS"`）—— 所以它是一份"准确但没人用的契约文档"。
- **`csrf_token` 明文回传是设计必需**：CSRF 双提交要求 JS 能读到该值（所以它的 cookie 刻意不是 HttpOnly）。风险点转移到"前端把它放哪里"—— 若落 `localStorage` 则 XSS 下可被读取。**该前端实现不在我的分区**，建议 F5/F6 代理确认（`frontend/src/utils/request.js` 与 stores）。

#### ② 口令与可写字段（`models/app_user.py` + `schemas/user.py`）

**结论：`password_hash` 当前不会回传前端，但防线是"靠纪律"而非结构约束；`role` 虽可由客户端提交却被服务端强约束，无越权；口令强度只有长度下限 6。**

- **`password_hash` 序列化风险**：全仓库 `password_hash` 只出现 5 处 —— 列定义（`models/app_user.py:21`）、长度常量（`services/constants.py:65`）、`row_to_dict` 的 docstring 举例（`utils/common.py:111`）、以及**唯一两处序列化点**：
  - `api/v1/endpoints/auth_routes.py:31` → `row_to_dict(user, exclude=("password_hash",))`
  - `services/user_service.py:60` → `row_to_dict(user, exclude=("password_hash",))`
  证据：`grep -rn "password_hash" backend/app` → 仅上述 5 处；`grep -rn "row_to_dict((user|current_user|u|created|updated|...)" backend/app` → 仅上述 2 处。
  ⇒ **当前无泄漏路径**。但所有接口都是 `response_model=ResponseModel`（`data: Any`），**没有** Pydantic 响应模型做 `exclude` 兜底 ⇒ 新增任何"返回用户"的代码路径一旦忘记 `exclude`，哈希会直接进 JSON。已在 `models/app_user.py` 加注释固化该约束；结构性修复见提案 2/4。
- **口令强度校验**：schema 层 `min_length=6`（`UserCreate.password`、`PasswordChange.new_password`、`UserUpdatePassword.new_password`），`max_length=128`；Service 层 `validate_length(..., min_len=PASSWORD_MIN_LEN=6)` 二次兜底（`user_service.py:177,272-276`）。**无复杂度/黑名单/字典校验** —— 代码注释明确写「复杂密码策略列为 P2，第一阶段仅做基本长度校验」（`user_service.py:176`）。`LoginRequest.password` 只有 `min_length=1`（登录不校验强度，正确）。哈希算法见 `utils/common.py::hash_password`（本分区外）。
- **可被客户端写入的字段清单**（这是"批量赋值越权"审查的核心交付）：

| 入口（路由） | Schema | 客户端可写字段 | 鉴权 | 服务端附加约束（已核） |
|---|---|---|---|---|
| `POST /api/v1/users` | `UserCreate` | `username`, `password`, **`role`**, **`scenario_id`** | `require_scenario_admin` | `role` 必须是 ROLES 之一；`role=SUPER_ADMIN` 直接 400 拒绝（不可经此接口创建）；`SCENARIO_ADMIN` 只能建 `SCENARIO_USER` 且 `scenario_id` 必须等于自己的绑定场景；场景必须存在 |
| `PUT /api/v1/users/{id}/scenario` | `UserUpdateScenario` | **`scenario_id`** | `require_scenario_admin` | 目标为 SUPER_ADMIN → 400；`scenario_id` 不能为 null（400）；`SCENARIO_ADMIN` 只能改本场景用户且只能改成本场景；场景必须存在 |
| `PUT /api/v1/users/{id}/password` | `PasswordChange` | `old_password`, `new_password` | 本人或管理员 | 非管理角色只能改自己；本人必须验旧密码（错误 → 400）；新密码长度 6-128；**成功后撤销该账号全部会话** |
| `PUT /api/v1/users/{id}/reset-password` | `UserUpdatePassword` | `new_password` | `require_scenario_admin` | `SCENARIO_ADMIN` 限本场景；长度 6-128 |
| `PUT /api/v1/users/{id}/status` | `UserUpdateStatus` | `status` ∈ {ENABLED, DISABLED} | `require_scenario_admin` | 仅值域校验（D7 自锁未拦） |

  - **`role` 可由客户端提交但无法越权**：不存在"普通用户自改 role"的入口（没有 update-role schema），且创建路径对 SUPER_ADMIN 硬拒、对 SCENARIO_ADMIN 强制降级为 SCENARIO_USER。⇒ **无可批量赋值的越权字段**。
  - **`username` / `role` 创建后不可修改**（无对应 update schema）—— 这是正确设计。
  - **`scenario_id` 普通用户不可自改**（只有管理级路由）。
  - 唯一可用性隐患：D7（管理员自锁）。

#### ③ `dataset.visibility` 默认值（`models/dataset.py`）

**结论：列默认值 `"platform"` 确实是"最宽可见"，但所有写入路径都按上传者角色显式覆盖，实际不构成默认越权；真正的风险只在"绕过 Service 直插"。**

## 7.1 relationship `lazy` 完整清单（本分区重点 7）

**事实**：本分区所有 relationship **一律未指定 `lazy`** ⇒ SQLAlchemy 默认 `lazy="select"`（访问时各发一条 SELECT）。

### （a）实际被代码遍历 → **真实 N+1**（按严重度排序）

| relationship | 遍历点 | N+1 规模 | 建议 |
|---|---|---|---|
| `ModelVersion.scenario` / `.dataset` / `.algorithm` / `.trainer` / `.publisher` | `services/model_version_service.py:139-147`（`_to_dict`），被**列表接口**调用：`get_list`（`:681`，page_size ≤ 200）、`list_training_tasks`（`:433`）、`get_default`（`:747`） | 最坏 **200 × 5 = 1000** 条额外 SELECT/请求 | `lazy="selectin"`（一次 IN 查询批量取回） |
| `Dataset.scenario` | `services/dataset_service.py:137-139`（`_to_dict`），被 `get_list`（`:215-217`）逐条调用 | 最坏 **200** 条额外 SELECT | `lazy="selectin"` |
| `InferenceRecord.model_version` → 再 `.scenario` / `.algorithm` | `services/inference_record_service.py:147-149,290,334,852`（列表接口逐条） | 每条记录 **1 + 2** 条额外 SELECT | `lazy="selectin"`（`model_version`）+ 对 ModelVersion 侧同批处理 |
| `AppUser.scenario` | `api/deps.py:102`、`services/user_service.py:50,131`、`api/v1/endpoints/auth_routes.py:54` | **已被 `joinedload(AppUser.scenario)` 显式覆盖** ⇒ 无 N+1 | 保持现状（这是全项目唯一正确 eager-load 的关系，可作为其他处的范式） |
| `UserAISetting.user` / `SituationSnapshot.scenario` / `AuthSession.user` | 无遍历点（service 只读 `user_id`/`scenario_id` 与 `row_to_dict`） | 无 | 保持 `select`，或改 `lazy="raise"` 以暴露误用 |

### （b）声明但全库零遍历（12 + 7 + 其余）—— 低风险，不建议改

- `AppUser`：`datasets`、`models_trained`、`models_published`、`inference_records`、`risk_events`、`handling_records`、`reports_generated`、`reports_targeted`、`thresholds`、`threshold_updates`、`threshold_audit_logs`、`audit_operations`（12 条，全库无 `.datasets`/`.reports_generated` 等访问点）
- `Scenario`：`users`、`datasets`、`model_versions`、`risk_events`、`snapshots`、`risk_thresholds`、`audit_logs`（7 条）。**注意**：`Scenario.datasets` 是已知陷阱 —— `services/dashboard_service.py:1991`、`:2193` 明确注释「**不要**改用 `dataset.scenario.datasets`，那条 relationship 会**绕过可见性过滤**」。⇒ 该 relationship 不仅未优化，而且**语义上危险**：建议 `lazy="raise"` 或干脆删除（删 relationship 不改表结构，但仍属模型公共接口 ⇒ 提案）。
- `Dataset`：`uploader`、`model_versions`、`risk_events`；`Algorithm`：`model_versions`、`risk_events`；`ModelVersion`：`inference_records`、`risk_events`。

### （c）实施注意（给 Lead）

`lazy="selectin"` 会让"取一页 model_version"额外固定多 5 条 SELECT（而不是 1000 条），且**在 session 关闭后仍可访问**（当前 `_to_dict` 在 session 内执行，所以只影响查询次数，不影响正确性）。若担心 `selectin` 在 `get_list` 的 count 查询上产生副作用，可改为在具体查询里 `.options(selectinload(...))`（**只改 service，不动模型**）——这是我推荐的更保守方案。
