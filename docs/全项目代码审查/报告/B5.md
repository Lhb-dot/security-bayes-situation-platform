### 3.4 D. 正确性隐患

**1) `@service_call` 把编程错误变成 500（协议点名的典型问题）—— 已修，但保留对外 500**

- 原实现：`except ServiceError` → 业务码；`except SQLAlchemyError` → 500；`except Exception` → 500。三个问题：
  1. `TypeError`（如 `None + 1`）、`ValueError`、`KeyError`、`AttributeError`、`IndexError` 这类**代码缺陷**与「数据库炸了」「网络超时」共用一条日志和同一个兜底，现场无法区分；
  2. `except Exception` 分支**没有 `rollback()`** → 抛异常后 session 仍是脏的，被连接池复用时会带出 `PendingRollbackError` 之类的次生故障；
  3. 兜底掩盖真实错误：`fail(500, "服务器内部错误")` 让调用方（含前端）无法区分「我的参数错了」与「后端崩了」。
- 已改（`base.py:45-91`）：新增 `_PROGRAMMING_ERRORS = (TypeError, ValueError, KeyError, AttributeError, IndexError)` 分支，日志文案 `Service 编程错误：<method> …` 并带 `logger.exception` 栈；**4 个分支统一 `self.db.rollback()`**（放在公共出口）。对外响应**逐字节不变**（仍 `fail(500, "服务器内部错误")`）——协议「行为不变优先」，且 `api/**` 的 `unwrap()` 只认 code/message，改文案会动前端契约。
- 仍未做（见 §8）：给编程错误回一个**可区分的内部 code**（如 5001）或仅在 `DEBUG` 下回栈，需要 Lead 与前端 F6a 协商；本区不动契约。
- 附：`service_call` 依赖 `self.db`，我核对过**没有任何模块级 `@service_call` 使用**（`grep -n "^@service_call" backend/app/**/*.py` 零命中），因此 `self` 一定是 `ServiceBase` 实例，`self.db.rollback()` 安全。

**2) 上传越权与路径穿越（`dataset_service.py`）—— 已修**

- 原 `upload_from_file`：先 `file_path.write_bytes(file_bytes)` **再**做角色校验 → 越权请求（例如 SCENARIO_ADMIN 往别人的场景传）会**先落盘**，随后 403 抛出，留下孤儿文件；且 `filename` 直接参与拼接，`filename="../../app/main.py"` 这类值会被写入 `data/<scenario>/` 之外。

### B5-P8（中优先级，X2 区 alembic 新迁移提案）：快照去重与保留策略

**问题**：`situation_snapshot_service.create_snapshot` 无去重/无锁（§3.4-7），表无唯一约束、无清理任务。
**提案（新迁移，不动历史迁移）**：
```python
# alembic/versions/<new>_add_situation_snapshot_guard.py
def upgrade():
    op.create_index(
        "uq_situation_snapshot_scenario_time",
        "situation_snapshot",

        unique=True,
    )
def downgrade():

```
外加保留策略（服务层或定时任务）：每个 `scenario_id` 只保留最近 N 条
