## 2. 死代码 / 死字段

### 2.1 死分支（已删）

**`_effective_groups` 第二遍的 `dataset.logical_id in CARRIER_LOGICAL_IDS` 是恒真死分支。**

原代码（L951-956 附近）：

```python
if dataset.logical_id in CARRIER_LOGICAL_IDS or fingerprint in carrier_fingerprints:
    key = CARRIER_GROUP_ID
else:
    key = fingerprint
```

第一遍 `carrier_fingerprints = {content_fingerprint(d) for d in datasets if d.logical_id in CARRIER_LOGICAL_IDS}` 与第二遍遍历的是**同一个 `datasets` 列表**，且 `content_fingerprint` 按 `dataset.id` 缓存，对同一 dataset 两次调用必返回同值。故 `dataset.logical_id in CARRIER_LOGICAL_IDS` ⇒ 该 dataset 的指纹已在 `carrier_fingerprints` 中 ⇒ 左操作数恒可被右操作数覆盖。

已改为（L957）：

```python
key = CARRIER_GROUP_ID if fingerprint in carrier_fingerprints else fingerprint
```

行为完全不变（`py_compile` EXIT=0，且上文已证明该分支在任何输入下都不改变结果）。**删除 2 行真实死代码。**

## 3. 已核实并修复的缺陷（4 处）

### 3.1 缺陷 1：`describe()` 的 `risk_rate` 把「无数据」伪装成「零占比」

- **位置**：`_DatasetReader.describe` 原 L886（现 L910）
- **现象**：`_percent(risk, total)` 在 `total == 0`（空表 / 文件缺失 / 表头缺失）时返回 `0.0`。前端 `ProfileNetwork/ProfilePower/ProfileGeological/ProfileFlightdeck` 统一走 `fmtPercent(item.risk_rate)`，渲染出 `0.0%`，与「真的 0% 风险」无法区分。
- **修法**：改用新增的 `_percent_or_none`，分母 0 时下发 `null`。
- **核实过程**：先 grep 了 `_percent` 的全部调用点（13 处），确认哪些调用点**必须**保留数值语义，再逐个判断。结论见 3.4。

### 3.2 缺陷 2：工频合格率 `frequency_pass_rate` 同类问题

- **位置**：`_power_telemetry_by_dataset` 原 L1672（现 L1698）
- **现象**：无 `PowerFrequencyHz` 列（或全为缺失）时 `len(frequency_values) == 0` → 原返回 `0.0`，前端 `ProfilePower.vue:208` 渲染「工频合格率 0.0%」，读者会误判为「电力质量全线不合格」。
- **修法**：`_percent_or_none(passed, len(frequency_values))`。

### 3.3 缺陷 3：`redundancy_rate` 在无文件时给 `0.0`

- **位置**：`_flight_redundancy` 原 L1851-1853（现 L1877-1880）
- **现象**：`file_count == 0` 时原返回 `0.0`，前端 `ProfileFlightdeck.vue:249` 渲染「冗余率 0.0%」，语义应为「无文件，未定义」。
- **修法**：返回 `None`。

### 3.4 连带修复：`_network_caliber_matrix` 的 `deviation` 潜在 `TypeError`

- **位置**：`_network_caliber_matrix` 原 L1516 区（现 L1542）
- **现象**：原代码 `round(rate / scene_rate, 4) if scene_rate else None`。缺陷 1 一旦让 `rate` 变为 `None`，当 `scene_rate != 0` 时会执行 `None / float` → `TypeError` → 被 `@service_call` 兜成 500。**这是修改缺陷 1 引入的连带风险，必须同时修。**
- **修法**：`if rate is not None and scene_rate else None`。

### 3.6 重要更正：`null` 目前**不会**让前端渲染出「—」

任务书给的修法前提是「下发 `null` 后前端已有的 `—` 渲染路径会生效」。**经核实这个前提不成立**：

`frontend/src/components/dashboard/dashFormat.ts`：

```ts
export const fmtPercent = (value: unknown, digits = 1): string => {
  const num = Number(value);
  if (!Number.isFinite(num)) return '—';
  return (num * 100).toFixed(digits) + '%';
};
```

`Number(null) === 0`，是有限数 → 走 `toFixed` → 仍渲染 `"0.0%"`。`fmtInt` 同款问题。

**所以本次修复的实际收益**是「后端不再伪造 `0.0`，契约上如实标注未定义」，前端观感**在 F7 修 `dashFormat.ts` 之前不变**。已把这一点写进 `_percent_or_none` 的 docstring，避免后人误以为已修完。前端修复方案见 §6 **B1-P1**。

**同时已验证不会引入前端崩溃**：`ProfilePower.vue:130` 的 `item.record_count * item.frequency_pass_rate` 与 `WorkspaceGeological.vue:60` 的 `item.risk_rate * 100`，在 JS 中 `null` 参与算术被强制转 0，不会抛异常。

## 4. 正确性核查（逐条回答任务书的 ①–⑤）

### ① `content_fingerprint` 的 `"missing:{logical_id}"` 会不会把多个缺失文件误判为同源？

**不会误判为「不同源」，但存在一处可辩护的过度合并。**

- 回退串含 `logical_id`，故**不同** `logical_id` 的缺失文件指纹必不相同 → 不会被并成一组。✅
- `"missing:..."` 前缀与正常指纹 `"{size}-{sha1}"` 命名空间不相交 → 缺失文件永远不会与正常文件碰撞。✅
- **唯一合并情形**：`datasets` 表约束是 `UniqueConstraint("logical_id", "version")`（`uk_dataset_logical_version`），**`logical_id` 本身不唯一**——同一 `logical_id` 的两个版本文件同时缺失时，两者指纹相同（`"missing:同id"`）→ 被并为同一同源组。
  - **判定**：这是**可辩护**的。同 logical_id 的两个版本本就互为同源衍生，缺文件时保守地只计一份，比重复计数更安全；且此时两个文件都读不到，样本量记 0，不影响任何数字。
  - **建议**：不修改。若将来要更精确，可在回退串里加 `version`，但那会让「同一 logical_id 不同版本」在文件正常时因内容相同而合并、在缺失时因版本不同而拆开 —— 反而制造不一致。**保持现状。**

### ② 两遍分组会不会 under-merge / over-merge？

- **Over-merge（过度合并）**：不会。除 carrier 白名单族外，分组键是**内容 SHA1**，内容不同必不同组。carrier 族内部本就是「同一批样本的三种编码」，合并是设计意图（见 `_effective_groups` docstring 与 `CARRIER_GROUP_ID` 注释）。
- **Under-merge（合并不足）**：唯一可能是 carrier 白名单成员的文件缺失，此时指纹为 `"missing:{id}"`，不再等于 `carrier_feature2_biaoqian` 的指纹（也是 `"missing:carrier_feature2_biaoqian"`，**只有同 id 才相等**）→ carrier 族会**裂开**成最多 3 个组。
  - **判定**：可接受。缺文件时该数据集样本量记 0，裂开后只是「有效数据集数」多算几个、样本量仍为 0，不会虚增任何数字。
  - **第二遍删除 `logical_id in CARRIER_LOGICAL_IDS` 是否加剧了这一点？** 需要单独论证：删除后，若 `carrier_feature2_biaoqian` 文件缺失，它的指纹 `"missing:carrier_feature2_biaoqian"` 仍会被第一遍放进 `carrier_fingerprints`（第一遍的筛选条件是 `logical_id in CARRIER_LOGICAL_IDS`，与文件是否存在无关），因此它自己**仍然**落进 `CARRIER_GROUP_ID`；而另外两份 carrier（`_lisan`、`paired_trail`）只要文件正常，指纹就不在集合里 → 各自成组。
  - **即：删除该分支前后，缺文件场景的行为完全一致。** 该分支在任何输入下都不改变结果（前面已证恒真），删除是安全的。✅

### ③ 0 分母路径会不会把 `NaN` 泄漏进响应？

**不会。** 逐条：

- `_percent`：`round(part / total, 4) if total else 0.0` —— `total` 为 0 时短路，不做除法。✅
- `_percent_or_none`：同结构，返回 `None`。✅
- `_risk_score`：`round(mean(scores) * 100)`，`scores` 非空才调用（`_risk_score` 内部对空列表返回 0）。✅
- `_mean` / `_stats`：内部经 `_finite()` 过滤，`inf`/`nan` 在 `_to_float`/`_num` 阶段就被转成 `None`。✅
- `_network_profile.traffic.retransmission_ratio`：`round(avg_retrans / avg_in, 4) if avg_in else 0`，有守卫。✅
- `_flight_profile.approach.abs_change_ratio_mean` 等：`_mean` 已过滤。✅
- **唯一残留隐患（低概率，仅报告）**：`_risk_score` 直接吃 `float(event.risk_score or 0)`。若数据库里 `risk_events.risk_score` 存了 `NaN`（PostgreSQL `double precision` 允许 `NaN`），`round(nan * 100)` 会抛 `ValueError: cannot convert float NaN to integer` → 被 `@service_call` 兜成 500。**`_finite` 没有覆盖这条路径**（`_score_bins`/`_daily_trend`/`_event_summary` 也都直接 `float(event.risk_score or 0)`）。
  - 影响面：`get_admin_overview`、`get_scenario_overview`、`get_workspace` 全部受影响。
  - 概率：写入侧若只由 `risk_view`/推理服务产生分数，则不会出现 `NaN`；未经核实（`RiskEvent` 的写入路径不在本分区）。**不修改**，仅提示 Lead 可加一行 `if not math.isfinite(score): score = 0.0`。

### ④ `_modeling_stats` 的单条 `group_by` + `count(*) FILTER` 是否对所有状态正确？

**正确。** 现 L1437-1445：

```python
select(
    ModelVersion.dataset_id,
    func.count(),
    func.count().filter(ModelVersion.status == MODEL_STATUS_PUBLISHED),
).where(ModelVersion.dataset_id.in_([...])).group_by(ModelVersion.dataset_id)
```

- `func.count()` = 该 dataset 的**全部**模型版本数（不分状态）→ `total` ✅
- `func.count().filter(status == PUBLISHED)` = 已发布数 → `published` ✅
- `draft = total - published`（L1454）→ 覆盖除 PUBLISHED 外的所有状态（含 DRAFT 与任何未来状态）。**注意**：字段名叫 `draft`，语义实为「非已发布」。当前 `MODEL_STATUS_*` 只有 DRAFT/PUBLISHED 两态，故等价；若将来引入 `ARCHIVED`，`draft` 会把归档也计进去 —— 命名与语义会脱钩。**仅报告，不改名**（改名属响应结构变更）。
- 无模型版本的 dataset 不会出现在查询结果里，但 L1449 `by_dataset.get(item.id, (0, 0))` 会为它合成 `(0, 0)` → 「数据白躺」仍然可见 ✅（这是该函数的核心目的，处理正确）
- SQL 方言：`count(*) FILTER (WHERE ...)` 是 PostgreSQL 原生语法 ✅；本地 SQLite 3.45.3 ≥ 3.30 亦支持 ✅
- 空 `datasets` 提前返回 `[]`（L1435），避免 `in_([])` 生成恒假条件 ✅

### ⑤ `get_profile` 的 N+1 复核

## 7. 复杂度与缓存分析

### 7.1 `_effective_groups` 两遍分组 —— 是否过度设计？

**不是。** 两遍是**必需**的：

- 只按内容指纹分组 → carrier 三份是「同一批样本的三种编码」（MD5 各不相同），会被拆成 3 组，导致有效样本量 3 倍重复计数。
- 只用白名单 `logical_id` 分组 → 漏掉 `carrier_track_company_v1`（其内容与 `carrier_feature2_lisan` 完全相同，但 logical_id 不在白名单里）。

第一遍算 carrier 指纹集合，正是为了**同时**覆盖这两种情况。第二遍的复杂度是 O(n) 字典操作，第一遍的 `content_fingerprint` 已被 `_FINGERPRINT_CACHE` 按 `dataset.id` 缓存。**保留。**

本次唯一改动是删掉第二遍里恒真的 `or dataset.logical_id in CARRIER_LOGICAL_IDS`（§2.1），让意图更直白：**判族只看指纹**。

### 7.2 `content_fingerprint` 缓存与失效

| 缓存 | key | 失效依据 | 评价 |
|---|---|---|---|
| `_HEADER_CACHE` | `dataset.id` | `(mtime, size)` | 正确 |
| `_ROW_CACHE` | `dataset.id` | `(mtime, size)` + 内存预算 LRU | 正确 |
| `_ROW_COUNT_CACHE` | `dataset.id` | `(mtime, size)` | 正确 |
| `_LABEL_STATS_CACHE` | `dataset.id` | `(mtime, size, label_field)` | 正确（含 label_field） |
| `_LABEL_VALUES_CACHE` | `dataset.id` | `(mtime, size, label_field)` | 正确 |
| `_FINGERPRINT_CACHE` | `dataset.id` | `(mtime, size)` | **仅此一处不含 `logical_id`** |

**`_FINGERPRINT_CACHE` 的窄缝**：缓存值 `"missing:{logical_id}"` 依赖 `dataset.logical_id`，但缓存键/失效判据里没有 `logical_id`。若 `logical_id` 被改而文件仍缺失（`mtime, size` 恒为 `(0.0, -1)`），会返回**旧的** `"missing:旧id"`。

**是否真实缺陷？否。** 论证：

1. `logical_id` 只能通过 `DatasetService` 的更新路径修改，而 `dataset_service._invalidate_dashboard_cache()`（L59-67）调用 `clear_dataset_caches()` 清空**全部** 6 个缓存，已覆盖 L319 / L435 / L459 / L498 四条写路径（create / update / delete / 批量）。
2. 即便某条未来新增的写路径漏了失效，后果也只是「同源分组键串了」，而两个文件都读不到（样本量记 0），不影响任何数字。

**判定**：**不作为缺陷报告，不修改**。若追求严谨，可把 `_FINGERPRINT_CACHE` 的失效判据改为四元组 `(mtime, size, logical_id)`，属可选加固。

### 7.3 `warm_dataset_caches` / `clear_dataset_caches`

- `warm_dataset_caches`：按文件体积升序 + 10s 预算 + 每个数据集 `try/except Exception` 独立跳过，**设计合理**。唯一的 `except Exception`（L684）带 `# noqa: BLE001` 与注释，是启动预热场景的正确取舍（一个坏文件不应阻断启动）。✅
- `clear_dataset_caches`：`global _ROW_CACHE_BYTES` + 锁内清 6 个缓存 + 归零计数，**正确**。✅
- 两者都在 `_CACHE_LOCK` 下操作，`_ROW_CACHE_BYTES` 的读写全部在锁内（L747-775 已核对）→ **无竞态**。✅

### 7.4 单请求复杂度小结

| 端点 | SQL | 主要 CPU |
|---|---|---|
| `get_admin_overview` | 1(scenarios) + 1(datasets) + 4(count) + 1(events) + 3(group_by) = **10** | 全部数据集 ARFF 解析（缓存命中后仅遍历） |
| `get_scenario_overview` | 1(scenarios) + 1(datasets) + 1(published group_by) + 1(events) + 1(thresholds) = **5** | 同上 |
| `get_profile` | **3** ✅ | 场景内数据集 ARFF 全量解析 |
| `get_workspace` | 1(scenario) + 1(events) + 1(thresholds) + 1(dataset) + 1(inference) + **2(lazy-load)** = **7** | 事件遍历（内存） |

`get_admin_overview` 的 10 条 SQL 全部是**固定条数**，逐场景循环里只有内存过滤（L1157-1159、L1296-1298），**无 N+1**。✅
