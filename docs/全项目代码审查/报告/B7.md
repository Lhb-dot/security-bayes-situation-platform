## 2. 改动摘要（每项一行）

1. **修 D-30 同型缺陷（本分区存在的理由）**：`_execute` 的 `SessionLocal()` 从 `try` 外移入 `try` 内，`db` 初始化为 `None`，`rollback()` / `close()` 判空 —— 与 B2 在 `report_generate_runner.py` 的修法完全同型。
2. **并发**：`_execute` 对 `job.status` / `job.error` / `job.finished_at` / `_fill(job, ...)` 的**写入侧**全部纳入 `_jobs_lock`，与 `get_job` / `get_job_record` / `list_jobs` 的读侧持锁对称（原写入侧完全无锁）。
3. **清理时效**：`_loop` 的 `queue.Empty` 空闲分支增加一次 `_purge_locked()` —— 原实现只在 `_register`（下一次提交）时清理，无新提交时过期终态任务连同 PDF 字节驻留到进程退出。
4. **文档**：`create_job` / `create_finished_job` docstring 明确「鉴权由调用方负责，本模块不做权限判断」（回应 P0 越权核查的结构性弱点）。
5. **未删除**任何函数 / 常量 / 导出名 / 方法签名；`services/__init__.py` 零改动。

### D. 正确性隐患

**D-1【已修 · P0 · 本分区存在理由】建会话失败 ⇒ 任务永久 RUNNING ⇒ 永不清理**

改前（`git show HEAD:...` 第 195 行）：

```python
    with _jobs_lock:
        job = _jobs.get(job_id)
    if job is None:
        return
    job.status = STATUS_RUNNING

    db = SessionLocal()          # ← 在 try 之外
    try:
        title, content, report_data = ReportService(db).load_export_source(job.report_id)
        exported = build_export(...)
    except Exception as exc:
        db.rollback()            # ← db 未建起来时这行本身也会炸
        job.status = STATUS_FAILED
        ...
    finally:
        job.finished_at = time.time()
        db.close()
```

失效链：`SessionLocal()` 抛异常（数据库不可用 / 连接池耗尽 / `DATABASE_URL` 失效）→ 异常在进入 `try` 前抛出 → 逃出 `_execute` → 被 `_loop` 的 `except Exception` 兜住只记日志 → `job.status` 永久停在 `RUNNING`、`job.finished_at is None` → `_purge_locked` 只清 `TERMINAL_STATUSES`（L169）⇒ **该任务连同 `content`（PDF 字节）永不被淘汰，进程级永久泄漏**；前端轮询永远看到 `RUNNING`。与 B2 在 `report_generate_runner._execute` 修掉的缺陷**完全同型**。

改后（与 B2 修法同型：会话创建移入 `try` + 判空）：

```python
    with _jobs_lock:
        job = _jobs.get(job_id)
        if job is None:
            return
        job.status = STATUS_RUNNING

    # SessionLocal() 必须放在 try 内：建会话失败（数据库不可用）也要把任务置为 FAILED。
    # 放在 try 外时异常会越过下面的 except，任务永远停在 RUNNING，前端会一直转圈，
    # 而 _purge_locked 只清终态任务 ⇒ 该任务连同 PDF 字节永久驻留内存。
    db = None
    try:
        db = SessionLocal()
        title, content, report_data = ReportService(db).load_export_source(job.report_id)
        exported = build_export(title, content, job.report_id, job.fmt, report_data)
    except Exception as exc:  # noqa: BLE001 - 后台任务：失败写进任务表
        if db is not None:
            db.rollback()
        with _jobs_lock:
            job.status = STATUS_FAILED
            job.error = str(exc)
        logger.exception("报告导出任务 %s 失败", job_id)
    else:
        with _jobs_lock:
            _fill(job, exported)
        logger.info("报告导出任务 %s 完成：%s", job_id, job.filename)
    finally:
        with _jobs_lock:
            job.finished_at = time.time()
        if db is not None:
            db.close()
```

**实测验证**（非 pytest，独立脚本，见 §6 命令 B）：`escaped_exception = None`、`status = FAILED`、`error = db down`、`finished_at_set = True` ⇒ 任务进入终态，可被 TTL 正常回收。
**注意**：`from app.db import SessionLocal` 保持**函数内导入**不动 —— 测试用 `patch("app.db.SessionLocal")` 打桩，移到模块顶层会破坏既有测试。

**D-2 越权（IDOR）** —— 见 §4 专节。结论：**未发现可利用的越权**。

**D-3 并发 / 共享字典无锁（已修写入侧）**

- 改前：读侧 `get_job` / `get_job_record` / `list_jobs` 持 `_jobs_lock`，但**写侧 `_execute` 完全无锁**（`job.status` / `_fill` 的 4 个字段 / `job.finished_at`），`_purge_locked` 的 docstring 却写明「调用方必须已持 `_jobs_lock`」—— 读侧持锁形同虚设。本次把写侧全部纳入同一把锁。
- 残留（可接受，未改）：`get_job_record` 在锁内返回**对象引用**，锁外读 `job.content`（`report_service.read_export_file`）→ 对象即使已被 `_purge_locked` 从 dict 弹出，引用仍存活，不会读坏数据；`_fill` 的写入顺序是 content→filename→media_type→status=DONE，读侧先判 `status` 再取 `content` ⇒ 不会出现「DONE 但 content 为 None」。`to_dict()` 在锁内执行 ✓。
- `is_running()` 读 `_started` 无锁：布尔读，无害。
- `_lock`（生命周期）与 `_jobs_lock`（任务表）从不嵌套获取 ⇒ 无死锁路径。

**D-4 TTL 惰性（已修）**：`_purge_locked` 只在 `_register`（= 下一次提交）触发 ⇒ 无新提交时过期终态任务永不回收。已在 `_loop` 的 `queue.Empty` 空闲分支补一次清理（空闲分支下该线程没有在跑的任务，全部在册任务要么 PENDING 要么终态，清理安全）。**实测**：`purged_without_new_submit = True`。

**D-5 单线程消费 ⇒ 提交速率无背压（未修，见 §5）**。

**D-6 `is_running()` 反映"意图"而非线程存活（未修 · 提案 B）**：`_started` 是布尔；若 `_loop` 因意外异常退出（`_queue.get` 之外的路径）则 `_started` 仍为 `True` ⇒ `submit_export` 继续收单、无人消费 ⇒ 任务永远 PENDING（无界泄漏，且 `EXPORT_JOB_MAX` 清不掉非终态）。提案：`return _started and _thread is not None and _thread.is_alive()`。**未实施理由**：会把「202 接受一个注定不执行的任务」变成「503 拒绝」，属对外表现变化，需 Lead 裁决（§7 提案 C）。

**D-7 `stop()` 不 join（未修 · 提案 C）**：`stop()` 只置 `_stop` 与 `_started=False`；若之后 `start()` 被再次调用，`_stop.clear()` 会让**尚未退出的旧线程**继续循环 ⇒ 理论上有两个消费者线程（daemon + 队列幂等，危害有限）。提案：`stop()` 中 `_thread.join(timeout=POLL_SECONDS*2)`。

**D-8 边界与空值**：`finished[:overflow]` 在 `overflow > len(finished)` 时安全切片 ✓；无除法（无分母为 0）✓；`job.content is None` 由 `report_service.read_export_file` 判 409 ✓；`exported.content/filename/media_type` 由 `build_export` 保证（`report_export.py`，B2 区）；`int(user_id)`/`int(report_id)` 若传 `None` 抛 `TypeError`（`create_job` 无 `@service_call`，会冒泡到 `report_service.submit_export` 的 `@service_call` → 500）—— 现有调用点均传非空值，属防御性缺口；`EXPORT_JOB_TTL_SECONDS` 配成负数会被接受（结果：终态任务立即被清，无害）；`_max_jobs()` 有 `max(1, ...)` 下限 ✓。

**D-9 过宽 except**：`_execute` 的 `except Exception`（后台任务必须写终态，已 `noqa: BLE001` + `logger.exception`）与 `_loop` 的 `except Exception`（单任务失败不拖垮执行器）—— **判定合理，非静默吞异常**；`_ttl_seconds`/`_max_jobs` 用窄 `except ValueError` ✓。

**D-10 `@service_call` 掩盖编程错误**：本文件**无** `@service_call`（模块级函数，非 Service 方法）⇒ 不受该风险影响。相关：`create_job` 无装饰器，内部 `TypeError` 会冒泡到 `submit_export` 的装饰器 → 500（语义可接受，非静默）。

**D-11 安全**：无 SQL 拼接（本文件不发查询，只把 `db` 交给 `ReportService`）；无路径拼接（文件名由 `build_export` 产出）；无密钥/明文凭据；`job_id = uuid.uuid4().hex`（122 bit 随机，不可枚举）。✓

**D-12 全局可变状态**：`_jobs` / `_queue` / `_stop` / `_started` / `_thread` 为模块级（docstring 已声明"进程内任务表"为有意设计）。**部署约束**：多 worker（`uvicorn --workers>1`）下每进程一份任务表 ⇒ 提交落在 A 进程、下载打到 B 进程会 404。当前 `main.py` lifespan 单进程起线程，符合设计；建议在 docstring 或部署文档中显式写明「本功能要求单 worker」。**注**：`report_generate_runner.py` 同样如此（B2 区，仅交叉提示）。

**D-13 时间字段**：用 `time.time()`（epoch 秒 float），**不是** `datetime.utcnow()` ⇒ 无弃用 API、无 naive/aware 混淆；与 `report_generate_runner` 一致，前端据此算「已进行秒数」✓。

## 5. 内存任务表无界增长判定 —— 本分区第三重点

**判定：是，本文件与 `batch_inference_runner` 同型存在无界增长，且更严重 —— `ExportJob` 直接持有 PDF 字节（`content: bytes`），不只是元数据。**

机制（4 条，逐条给行号）：

1. **非终态永不淘汰**：`_purge_locked`（L172）只清 `job.status in TERMINAL_STATUSES` 的任务；PENDING/RUNNING 一条都不清（`tests/test_report_export_async.py::test_pending_job_is_never_purged` 把该行为**固化为预期**）。
2. **`EXPORT_JOB_MAX=50` 不是硬上限**：`overflow = len(_jobs) - _max_jobs()`，可淘汰集合只有终态任务；若在册 100 条中 60 条是 PENDING/RUNNING，则一条都清不掉，dict 稳定停在 100+。该配置实际只约束"已完成任务的留存量"。
3. **队列无 `maxsize`**：`_queue: queue.Queue()`（L45）无上界，`create_job` 的 `_queue.put()` 永不阻塞 ⇒ **零背压**。提交速率只受 HTTP 层与 `_export_inputs` 的一次 DB 查询限制；消费侧是**单线程**、PDF 渲染 1–2 s/份 ⇒ 1000 个并发 POST 立刻堆出 1000 条 PENDING。
4. **TTL 惰性**：`EXPORT_JOB_TTL_SECONDS=900` 只在 `_register` 时检查；无新提交时，50 条终态任务连同 PDF 常驻到进程退出。**本次已在 `_loop` 空闲分支补清理**（§3 D-4），此项已缓解。

**最坏常驻内存估算**（单进程）：

- 终态产物：`50 × 单份 PDF`。报告含图表，单份 PDF 估 0.1–2 MB ⇒ **5 MB–100 MB**（这是稳态上限，因为终态可被 overflow 淘汰）。
- 非终态元数据：`N × (ExportJob ≈ 300 B + dict/queue 槽位) ≈ 1 KB/条`，**N 无上界**。灌 10 万条 ≈ 100 MB 仅对象。
- 累积产物：每条完成后都留下 PDF 并（在 TTL 内）不可清 ⇒ 10 万条 × 0.5 MB ≈ **50 GB**，实际会先 OOM。
- **触发条件**：任一已登录账号（DB 中 21 个 users 之一）循环 `POST /api/v1/reports/{report_id}/export/jobs?format=pdf`（只需能看到**自己**的一条报告，不需要管理员权限）⇒ **认证后自我 DoS / 内存耗尽**（不是越权，是可用性）。

**修复提案**（未实施，理由：拒绝提交的新错误语义必须落在 `report_service.py::submit_export`，属 B2 区 ⇒ §7 提案 E）：

- **方案 A（推荐）**：`create_job` 登记前统计非终态任务数，超上限即拒绝；`submit_export` 转 `ServiceError(503, "导出任务排队已满，请稍后重试")`；同时 `_queue = queue.Queue(maxsize=...)` 与 `put_nowait` 保持一致。
- **方案 B（本次已实施部分）**：空闲分支清理（解决 D-4 的"不回收"），但不解决"提交速率无上限"。
- **方案 C**：终态 `content` 落临时文件、内存只留路径（与 docstring「不值得为它建表/落文件」的设计取向相悖，改动大）。
