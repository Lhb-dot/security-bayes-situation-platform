# 单端口算法服务可行性分析

> 目标：把 12313–12319 这 7 个 Java 算法端口收成 1 个，由请求信息决定调用哪个算法。
> 本文只做可行性分析，未修改任何代码。所有结论均来自实测（jar 校验和、`javap` 反射、模型文件字节扫描）。

---

## 一、结论

**可行，但"把所有 jar 拍平成一个 fat jar"这条路走不通。**

| 方案 | 端口数 | 风险 | 建议 |
|---|---|---|---|
| A. 1 个 JVM + 双类加载器隔离 | 7 → **1** | 中（需重构调度层） | 目标形态 |
| B. 先合并 5 个算法服务，PMWNB 不动 | 7 → **3** | 低（不动 classpath） | **建议先做这步** |
| C. 拍平成一个 fat jar / 一个 `-cp` | 7 → 1 | **高，必坏** | 不要做 |

原因：5 个算法 jar 和 `pmwnb-service.jar` 之间存在 **10 个同名不同实现的类**，且**已训练模型里序列化嵌入了这些类**。拍平后必然有一方反序列化失败或行为静默改变。

## 二、现状实测

### 2.1 端口与产物

| 端口 | 进程 | jar | 作用 |
|---|---|---|---|
| 12313 | `PmwnbService` | pmwnb-service.jar（27 MB） | PMWNB `/train`、`/predict`（薄版） |
| 12314 | `PredictServer` | predict-service.jar（8 KB） | PMWNB `/predict`（带可解释性） |
| 12315 | `NbAlgorithmService` A2WNB | a2wnb-service.jar | A2WNB `/train` `/predict` |
| 12316 | `NbAlgorithmService` CAVWNB | cavwnb-service.jar | CAVWNB |
| 12317 | `NbAlgorithmService` EMAWNB | emawnb-service.jar | EMAWNB |
| 12318 | `NbAlgorithmService` MAWNB | mawnb-service.jar | MAWNB |
| 12319 | `NbAlgorithmService` DIWNB | diwnb-service.jar | DIWNB |

### 2.2 关键发现 1：5 个算法 jar 是同一个文件

```
97b5c0450bea7a9cbab253d884a0f4f6  a2wnb-service.jar
97b5c0450bea7a9cbab253d884a0f4f6  cavwnb-service.jar
97b5c0450bea7a9cbab253d884a0f4f6  emawnb-service.jar
97b5c0450bea7a9cbab253d884a0f4f6  mawnb-service.jar
97b5c0450bea7a9cbab253d884a0f4f6  diwnb-service.jar
```

89518 字节，MD5 完全一致。每个 jar 里都装了 **全部 4 个算法族**（`weka/classifiers/zh/A2WNB`、`zh/CAVWNB`、`zh/MVCAVWNB`、`mkx/DIWNB`）+ 同一个 `NbAlgorithmService`。

**也就是说，"一个算法一个端口"目前已经退化成"同一个程序起了 5 次"，唯一区别是启动时的第 2 个命令行参数。**

### 2.3 关键发现 2：服务本身已经是通用的

`backend/java/NbAlgorithmService.java`：

- `classNameFor(code)`（第 67 行）已经实现了算法编码 → 实现类的路由；
- `buildExplain()`（第 194 行）已经在**运行时用 `instanceof`** 分辨 `CAVWNB / MVCAVWNB / EMAWNB / DIWNB_HE / A2WNB` 五种算法并分别组装解释数据；
- 唯一的"单算法"痕迹是静态字段 `private static String algorithmCode;`（第 48 行），它只在 4 处被使用：`/health` 回显、`createClassifier()` 选实现类、`/train` 指标里的 `algorithm` 字段、`buildExplain()` 里的 `algorithm_details.algorithm_code`。

**要把 `algorithmCode` 从"启动参数"改成"请求参数"，改动量约 20–40 行。**

### 2.4 关键发现 3：端口映射只存在于两个地方

- `backend/app/services/algorithm_config.py` 第 12–18 行：`ALGORITHM_SERVICE_URLS` 字典（5 个 URL）+ `PMWNB_SERVICE_URL` + `PREDICT_SERVICE_URL`；
- `start_all.ps1` 第 98–152 行：7 次 `Start-Process java`。

前端**不直连**这些端口（`frontend/vite.config.ts` 的 proxy 只把 `/api` 转到 12312）。数据库 `algorithm` 表里也**没有** endpoint/port 字段，算法编码是硬编码字典（`app/services/constants.py` 的 `ALGORITHM_CODES`）。

→ **改动面是收敛的，没有隐藏的配置来源。**

### 2.5 关键发现 4：Python 侧早就知道该用哪个算法

`training_executor.execute_algorithm_training(code, ...)` / `execute_algorithm_predict(code, ...)` 的 `code` 来自调用方（`model.algorithm.code`，DB 里的真实算法）。现在的做法是**用 code 查 URL**；改成"用 code 填请求体字段"是等价的，不需要新增任何决策逻辑。

## 三、真正的阻碍：两套 Weka 世界不能拍平

`pmwnb-service.jar`（6025 个 class）与算法 jar（46 个 class）之间有 **10 个同名但内容不同的类**：

```
lbfgsb/Bound            lbfgsb/FunctionValues     lbfgsb/Result
lbfgsb/DifferentiableFunction  lbfgsb/IterationsInfo  lbfgsb/StopConditions
lbfgsb/LBFGSBException  lbfgsb/Minimizer
weka/classifiers/trees/RandomForest2
weka/estimators/DiscreteEstimator
```

### 3.1 差异（`javap -p -constants` 实测）

| 类 | 算法 jar 里的（compat） | pmwnb-service.jar 里的（weka） |
|---|---|---|
| `DiscreteEstimator` | serialVersionUID = **1**，字段 `counts` / `sum`，**多一个 `getProbability_laplace(int)`** | serialVersionUID = **-5526486742612434779**，字段 `m_Counts` / `m_SumOfCounts` / `m_FPrior` |
| `RandomForest2` | serialVersionUID = **1**，2143 字节简化壳 | serialVersionUID = **-2260823972777004705**，12242 字节真 Weka 实现 |
| `lbfgsb/Minimizer` | 纯 Java 梯度下降（源码注释：避开 native lbfgsb_wrapper） | 真 L-BFGS-B 封装 |

### 3.2 两侧互相依赖对方"独有"的成员

`javap -c` 统计各自实际调用的 `DiscreteEstimator` 方法：

| 调用方 | 调用的方法 |
|---|---|
| `weka.classifiers.bayes.PMWNB.CAVWNB.CAVWNB` | `addValue`、`getProbability` |
| `weka.classifiers.bayes.PMWNB.CAVWNB.WANBDistribution` | `getCount`、`getNumSymbols`、`getSumOfCounts` |
| `weka.classifiers.zh.CAVWNB.WANBDistribution` | `getNumSymbols`、**`getProbability_laplace`** ← 只有 compat 版有 |

→ **compat 版是所有被调用方法的超集**，但 compat 版**缺少** weka 版的 `getCapabilities()` / `getRevision()`，且 serialVersionUID 不同。

### 3.3 致命点：已训练模型里嵌了这些类

扫描 `backend/storage/models/*.model`：

| 模型 | 内含 `weka.estimators.DiscreteEstimator` | 内含 `RandomForest2` |
|---|---|---|
| `pmwnb_mv33.model` | ✓（**weka 版**，文件中出现 UID `b34df99692ae20a5`） | ✓（weka 版） |
| `a2wnb_mv29.model` | ✓（compat 版） | — |
| `cavwnb_mv32.model` | ✓（compat 版） | — |
| `emawnb_mv31.model` | ✓（compat 版） | ✓（compat 版） |
| `mawnb_mv30.model` | ✓（compat 版） | ✓（compat 版） |
| `diwnb_mv34.model` | — | — |

（另：5 个算法模型的顶层类都是 `com.security.bayes.nbservice.NbAlgorithmService$FilteredClassifierWithDiscretize`。）

**拍平 classpath 后，只有一份 `DiscreteEstimator` 能生效：**

- **compat 版赢** → 读 `pmwnb_mv33.model` 时 serialVersionUID 不匹配 → `InvalidClassException`，**PMWNB 预测直接抛错**；
- **weka 版赢** → `zh.CAVWNB.WANBDistribution.getProbability_laplace` → `NoSuchMethodError`，**CAVWNB / EMAWNB / MAWNB / A2WNB 全部不可用**。

另外 `lbfgsb` 两边都在真用（PMWNB 的 CAVWNB 有 7 个类引用它，NB 侧 6 个），拍平会让其中一方的优化器被替换 → **训练指标静默变化**：不报错，但同一个数据集跑出来的准确率会不一样。

### 3.4 结论

**不能合并 jar，也不能把所有 jar 丢进同一个 `-cp`。**

## 四、可行方案

### 方案 A（推荐目标形态）：1 个 JVM + 2 个子类加载器，1 个端口

一个薄调度进程监听 1 个端口，按请求里的 `algorithm_code` 选"世界"，把请求交给对应类加载器内的服务处理：

| 世界 | 子类加载器 classpath | 覆盖范围 |
|---|---|---|
| NB 世界 | `[nb-algorithms.jar, pmwnb-service.jar]` | A2WNB / CAVWNB / EMAWNB / MAWNB / DIWNB |
| PMWNB 世界 | `[pmwnb-service.jar]` | PMWNB |

两个 loader 的 parent 设为 platform loader、**不走父委派**，则 NB 世界里的 compat 类依旧覆盖 weka 类 —— **和今天 `java -jar nb.jar`（`Class-Path: pmwnb-service.jar`）的加载顺序逐字节一致**。对象不跨 loader 边界（一个请求全程在同一个世界里处理完），`SerializationHelper.read` 用调用类的 loader，反序列化也照旧正确。

代价：weka 核心会被加载两份（metaspace 多几 MB，可忽略）。

**改动面**

- Java
  - `NbAlgorithmService`：`algorithmCode` 由静态字段改为请求级（`/train`、`/predict` 从请求体读 `algorithm_code`；`/health` 改为回显支持列表）；
  - `PmwnbService.handlePredict` 与 `PredictServer` 的 `buildExplain` 合并（纯代码搬移，无新逻辑），`PredictServer` 整体删除；
  - 新增一个调度 `main`（按 code 路由到对应 loader）。
- Python（2 个文件，约 10 行）
  - `algorithm_config.py`：5 个 `ALGORITHM_SERVICE_URLS` + `PREDICT_SERVICE_URL` → 1 个 base URL；
  - `training_executor.py`：`/train`、`/predict` 请求体里带上 `algorithm_code`。
  - **响应体形状不变** → `app/schemas/explanation_contract.py`、`explanation_service.py` 与前端全部不受影响。
- `start_all.ps1`：7 次 `Start-Process java` → 1 次；端口兜底清理列表从 8 个降到 2 个。

### 方案 B（零风险，建议先做）：只合并 5 个算法服务

既然 5 个 jar 本来就一样，直接起 1 个进程、请求里带 `algorithm_code` 即可。

- 端口：12313–12319 → **12313 + 12314 + 1 个新端口 = 3 个**
- **不动 classpath、不碰 pmwnb 世界 → 无任何序列化风险**
- 改动面：`NbAlgorithmService` 请求级 `algorithmCode` + Python 2 个文件 + `start_all.ps1`
- 可以当作方案 A 的第一步，单独验证一轮全算法训练 + 预测

### 方案 C（不要做）：拍平 fat jar

见第三节。

## 五、无论选 A 还是 B 都要接受的代价

1. **训练并发下降**。现在 7 个 JVM 各有 4 线程池；合并后共用一个池。`/train` 是 CPU 密集、`TRAIN_TIMEOUT` 600 秒，必须把池调大或给训练单独排队，否则一个慢训练会堵住所有预测请求。
2. **故障隔离消失**。现在某个算法 JVM 崩了其它还能用；合并后是单点。`start_all.ps1` 里"按端口杀进程"的兜底也会变粗（原来能只杀一个算法）。
3. **模型缓存集中**。`MODEL_CACHE` 从"每进程只缓存自己算法的模型"变成"一个进程缓存全部"。目前只有 6 个模型，影响很小；模型数量上来后需要加淘汰策略。
4. **重启粒度变粗**。以前能单独重启一个算法服务，合并后要全停。
5. **换来的收益**：启动从 7 次 JVM 冷启（`start_all.ps1` 里每个还要等 20–30 秒探活）降到 1 次；端口占用从 8 个降到 1 个。

## 六、顺手发现的问题（未做任何改动）

1. **`scripts/build_nb_algorithm_jars.ps1` 里 `New-AlgorithmJar` 的 `$Entries` 参数完全没被使用**。函数体实际执行的是 `jar cfm $target $manifest -C $classes .`，把整个 `classes` 目录打进去 —— 这正是第二节"5 个 jar 字节相同"的原因。要么补上按算法裁剪条目的逻辑（用 `$Entries` 过滤），要么删掉这个死参数。**这是个真实的功能缺陷，不只是代码风格问题。**
2. **`predict-service.jar`（12314）与 `PmwnbService`（12313）的 `/predict` 逻辑几乎重复**，唯一区别是前者多了 PMWNB 可解释性输出（`views` / `view_weights` / `feature_evidence` / `algorithm_details`）。做合并时 `PredictServer` 可以整体删掉，把 `buildExplain` 搬进 `PmwnbService` —— 这一步单独做就能把端口从 7 降到 6，且零风险。
3. **`NbAlgorithmService$FilteredClassifierWithDiscretize` 是 private static 内部类，但被写进了 5 个模型文件**。重构时**类名和包名不能改**，否则历史模型全部读不出来。

---

## 七、建议

1. 先做**方案 B**（合并 5 个算法服务，端口 7 → 3），跑一轮全算法训练 + 预测验证；
2. 再单独做"`PredictServer` 并入 `PmwnbService`"（端口 3 → 2），同样零风险；
3. 最后评估是否上**方案 A**（2 → 1），此时才需要引入双类加载器调度层。

这样每一步都能独立验证、独立回滚，不会一次引入序列化风险。

## 附录：PMWNB 和其余 5 个算法到底差在哪（回答"不都是 NB 吗"）

**是，都是 NB 家族，而且 PMWNB 内部就装着 CAVWNB。** 不能合到一起的原因不在算法层，在**它们各自需要一份被改过的 Weka 核心**，而两份改法互斥。

### A. 算法层其实不冲突

PMWNB 的 CAVWNB 在 `weka.classifiers.bayes.PMWNB.CAVWNB` 包下，NB 世界的 CAVWNB 在 `weka.classifiers.zh.CAVWNB` 包下，**FQCN 不同，放一起本来没问题**。

而且它们是**同一份研究代码**。diff `algorithm-src/NB/CAVWNB/` 与 `algorithm-src/PMWNB/weka-src/.../CAVWNB/` 共 17 个文件：

- 16 个文件差异**只有 package 声明、注释换行、代码缩进**；
- NB 版多一个 `WANBDistribution.evidenceWeightForBinaryClassification()`（可解释性用）；
- PMWNB 版多一段 `offset` 计算；
- NB 版多一个文件 `CAVWNB_MSE.java`。

→ 同一份 CAVWNB，被 fork 成了两个包名下的两份副本。

### B. PMWNB 是"套在 CAVWNB 外面的元分类器"

不是并列关系，是**包含关系**。`PMWNB.buildClassifier()` 的流程：

```
PMWNB
├── view1：weka.filters.unsupervised.attribute.Discretize（EWD，10 bins，无监督）
│   └── PMWNB_L 集成 → 5 个 CAVWNB
│         base / SPODE-label / SPODE-prob / RF-label / RF-prob
└── view2：weka.filters.supervised.attribute.Discretize（MDLP，有监督）
    └── PMWNB_L 集成 → 5 个 CAVWNB
          base / SPODE-label / SPODE-prob / RF-label / RF-prob

最终概率 = view1 与 view2 的概率平均
```

而 CAVWNB 本身是单视图的类×属性值加权贝叶斯。**PMWNB = 2 个基础视图 × 5 个子模型的矩阵加权集成**（`PredictServer` 里那 10 个 `distributionForSubmodels` 名字就是这么来的），CAVWNB 是它的零件。

### C. 真正的分岔：打包方式不同，Weka 核心被改了两遍

| | PMWNB 世界 | NB 世界 |
|---|---|---|
| 产物 | `pmwnb-service.jar`，27 MB / **6025 个 class** | 5 个算法 jar，89 KB / **46 个 class**（5 个文件字节相同） |
| 来源 | Maven 打包的**完整 Weka 3.8 发行版** + PMWNB 插件（manifest：`Created-By: Maven JAR Plugin 3.5.0`，`Java-Version: 8`） | 研究者交付的**裸 `.java` 源码**（目录名就是 `algorithm-src`），用 `javac -cp pmwnb-service.jar` 手工编译 |
| Weka 核心 | **官方原版** | **被 compat 类覆盖** |

研究者那批源码需要几个**官方 Weka 里根本不存在**的东西，所以补了 compat 类（源码在 `backend/java/compat/`，注释写得很直白）：

| compat 类 | 为什么需要 | 覆盖了谁 |
|---|---|---|
| `weka.estimators.DiscreteEstimator` | CAVWNB 的 `WANBDistribution` 要调 `getProbability_laplace(int)`，官方没有 → 整个重写 | 官方 `weka.estimators.DiscreteEstimator` |
| `weka.classifiers.trees.RandomForest2` | MVCAVWNB 的 `RF_m` 要调 `distributionForInstance1/2/_c_p/_c_p_x`，官方 RandomForest 没这些按属性展开的辅助方法 → 写了个简化壳 | 官方 `weka.classifiers.trees.RandomForest2` |
| `lbfgsb.*`（8 个类） | 官方版依赖 **native** 的 `lbfgsb_wrapper` 库 → 换成纯 Java 梯度下降 | 官方 `lbfgsb.*` |
| `weka.classifiers.bayes.WANBIA` | A2WNB 引用了它，但交付的源码包里没有这个类 → 用 `NaiveBayes` 顶替 | **不冲突**：pmwnb-service.jar 里没有这个类，NB 侧是纯新增 |

**所以冲突点不在算法，在 Weka 核心那 10 个类上。** 同一个类名 `weka.estimators.DiscreteEstimator`，一份是官方原版，一份是研究者改过的 —— 一个 JVM 只能加载一份。

### D. 那能不能"统一成一份"？

逐条看，都走不通：

| 统一方向 | 后果 |
|---|---|
| 让 NB 用**官方原版** | `zh.CAVWNB.WANBDistribution.getProbability_laplace` → **`NoSuchMethodError`**，CAVWNB / EMAWNB / MAWNB / A2WNB 全部不可用 |
| 让 PMWNB 用 **compat 版** | `DiscreteEstimator` 单看是可行的（PMWNB 只调 `addValue` / `getProbability` / `getCount` / `getNumSymbols` / `getSumOfCounts`，compat 版全都有）；**但 `RandomForest2` 不行** —— compat 版是完全不同形状的类，而 `PMWNB.PMWNB.RF_m` 持有官方 `RandomForest2` 实例并已写进 `pmwnb_mv33.model` |

### E. 冲突已经"烧进"磁盘上的模型文件

实测扫 `backend/storage/models/*.model`：

| 模型 | 内含 `DiscreteEstimator` | 内含 `RandomForest2` |
|---|---|---|
| `pmwnb_mv33.model` | ✓ **官方版**（文件中出现 UID `b34df99692ae20a5`） | ✓ **官方版** |
| `a2wnb_mv29.model` | ✓ compat 版 | — |
| `cavwnb_mv32.model` | ✓ compat 版 | — |
| `emawnb_mv31.model` | ✓ compat 版 | ✓ compat 版 |
| `mawnb_mv30.model` | ✓ compat 版 | ✓ compat 版 |
| `diwnb_mv34.model` | — | — |

→ 合并 classpath 后无论哪一版胜出，都有一批**已训练模型读不出来**（`InvalidClassException`），必须全部重训。

### 一句话

**算法上是同一家人，PMWNB 甚至把 CAVWNB 当零件用；分不开是因为它们各自依赖一份被改过的 Weka 核心，而这两份改动在 10 个类上互相排斥，并且已经序列化进了模型文件。** 所以正确的做法不是"合成一个 jar"，而是"一个进程里放两个互不干扰的类加载器"。

## 八、"把所有源码给你，能不能不改功能地合并？"

分两种"合并"，只有一种满足"不改功能"。

### 方案 1（可以，且有把握）：不动算法源码，只加一层调度

**不需要任何源码。** 做法不是合并 classpath，而是**一个 JVM 里放两个隔离的子类加载器**：

| 世界 | 子类加载器 classpath | 与今天的关系 |
|---|---|---|
| NB | `[算法jar, pmwnb-service.jar]` | 加载顺序**逐字节一致** |
| PMWNB | `[pmwnb-service.jar]` | 加载顺序**逐字节一致** |

两个 loader 都不走父委派、对象不跨边界 → 每个算法看到的字节和今天完全相同，连优化器都是今天那一版。**功能不变是可以论证的，不是"应该没问题"。**

需要改的只在外围，**不碰任何算法类**：

- `NbAlgorithmService`：`algorithmCode` 由静态字段改为请求级（这是外壳类，不是算法）；
- 新增一个调度 `main`；
- Python 侧 2 个文件带上 `algorithm_code`。

**红线**：`NbAlgorithmService$FilteredClassifierWithDiscretize` 的**类名、包名、`serialVersionUID`（=1）不能动** —— 5 个模型文件里写着这个名字。加方法可以，改字段不行。

**一个实现细节**：`org.json`（30 个类）只在 `pmwnb-service.jar` 里，NB jar 靠 `Class-Path` 拿到它 —— 也就是说两个子加载器会各自持有一份 `org.json`。因此**调度器跨边界只能传原始字符串**（请求体 / 响应体），不能传 `JSONObject` 实例，否则会 `ClassCastException`。`com.sun.net.httpserver` 属于 JDK，交给 platform loader 即可。

### 方案 2（做不到"不改功能"）：真正合并成一个 classpath

把两边源码编到一起，逐类看：

| 冲突类 | 能否统一 | 依据 |
|---|---|---|
| `WANBIA` | ✅ **本来就无冲突** | pmwnb-service.jar 里没有这个类（`jar tf` 计数为 0），NB 侧是纯新增 |
| `DiscreteEstimator` | ⚠️ 技术可行，但**必须重训** | compat 版 = "官方版 + `getProbability_laplace`"；PMWNB 只调 `addValue`/`getProbability`/`getCount`/`getNumSymbols`/`getSumOfCounts`，compat 全有。但两边模型嵌的 UID 不同（`1` vs `-5526486742612434779`），已有模型全部读不出来 |
| `RandomForest2` | ❌ **源码不全** | 官方源码在仓库里（`algorithm-src/PMWNB/weka-src/.../trees/RandomForest2.java`，666 行，UID `-2260823972777004705`），但它调用 `m_bagger.distributionForInstance1/2` —— **需要一份被改过的 `RandomForest`，那份源码不在仓库里**（pmwnb-service.jar 的 `RandomForest` 也没有这两个方法）。这正是现在用 compat 简化壳的原因 |
| `lbfgsb`（8 个类） | ❌ **做不到不改功能** | PMWNB 用真 L-BFGS-B，NB 用纯 Java 梯度下降。**两边现在就在用不同的优化器** —— 同一份 CAVWNB 源码训练出的权重本来就不一样。合并后只能留一个 → 必有一方训练结果改变 |

**结论：方案 2 不是"不改功能"，是"改功能 + 重训全部模型"。** 而且它还缺源码 —— 需要的是：**被改过的 `weka.classifiers.trees.RandomForest`**（带 `distributionForInstance1/2`）与**原生版 `lbfgsb`**（或其 native 库）。

### 顺带发现：一份官方源码在仓库里躺着但从未被编译

`algorithm-src/PMWNB/weka-src/src/main/java/weka/classifiers/trees/RandomForest2.java`（666 行，真实现）**从未进入编译流程** —— `scripts/build_nb_algorithm_jars.ps1` 只编译 `backend/java/compat/` 和 `algorithm-src/NB/`，不含 `algorithm-src/PMWNB/weka-src/`。

也就是说 EMAWNB / MAWNB 现在用的 RF 是那个简化壳，不是这份真实现。要让它们与 PMWNB 内部的 RF 行为对齐，需要补齐那份被改过的 `RandomForest` 源码 —— 但这是**行为变更**，需要单独确认，且要重训模型。

### 建议

走**方案 1**。现有 jar 本身就是最好的"源码" —— 它们是已经跑通过的二进制，任何重新编译都是在引入变量。

## 九、六个算法是不是真的六个（不是同一个算法伪装六份）

**是六个不同的实现，有硬证据。** 但有一个需要说清楚的边界：MAWNB 和 EMAWNB 共享同一套三视图架构。

### 证据 1：同一数据集上跑出六组不同指标

`model_version` 表里 6 个已发布模型都是同一份数据集（7556 条样本）：

| 算法 | 端口 | accuracy | f1 | 训练耗时 | 模型体积 |
|---|---|---|---|---|---|
| PMWNB | 12313 | 0.9496 | 0.9494 | 19.4 s | 49.7 MB |
| A2WNB | 12315 | 0.9672 | 0.9671 | 3.9 s | 9.3 MB |
| CAVWNB | 12316 | 0.9738 | 0.9738 | 10.1 s | 58 KB |
| MAWNB | 12318 | 0.9809 | 0.9809 | 33.2 s | 15.4 MB |
| DIWNB | 12319 | 0.9846 | 0.9846 | 77.0 s | 4.0 MB |
| EMAWNB | 12317 | 0.9850 | 0.9850 | 147.9 s | 103.5 MB |

六组互不相同的准确率；训练耗时跨度 **3.9 s → 147.9 s（38 倍）**；模型体积跨度 **58 KB → 103.5 MB（约 1800 倍）**。同一个算法不可能同时满足这三点。

### 证据 2：模型文件内部结构完全不同

扫 `storage/models/*.model` 里嵌的类：

| 模型 | 内部嵌入的类 | 说明 |
|---|---|---|
| `a2wnb_mv29` | `RODE`、`RODE$RODANB` | 两阶段：RODE 在前 |
| `cavwnb_mv32` | `WANBDistribution` | 只有一个单视图分布 |
| `diwnb_mv34` | `KNNs_hard` | 第二视图由 KNN 生成 |
| `mawnb_mv30` | `MVCAVWNB.RF_m`、`SPODE`、`WANBDistribution` | 三视图 |
| `emawnb_mv31` | `MVCAVWNB.RF_m`、`SPODE`、`WANBDistribution` | 三视图（与 MAWNB 同结构） |
| `pmwnb_mv33` | `PMWNB_L`、`CAVWNB`、`RF_m`、`SPODE` | 双层集成 |

### 证据 3：源码里的机制差异

| 算法 | 实现类 | 机制 |
|---|---|---|
| A2WNB | `zh.A2WNB.A2WNB` | `RODE` 为每个属性生成一个预测标签并插回数据集（属性数翻倍），再用第二阶段分类器训练 |
| CAVWNB | `zh.CAVWNB.CAVWNB` | 单视图；对"类 × 属性值"三元组加权，权重由 `lbfgsb` 最小化 MSE / MASP 目标函数得到（带 L2 正则） |
| MAWNB | `zh.MVCAVWNB.MVCAVWNB` | 三视图（原始属性空间 / SPODE 标签空间 / RF 标签空间），各一个 CAVWNB，**固定等权 1/3** |
| EMAWNB | `zh.MVCAVWNB.EMAWNB` | **同样三视图**，但每个测试样本调 `LearningViewWweight()` **动态学视图权重**（基于到训练样本的距离，k=30，10 折），且 SPODE / RF 是**集成数组** |
| DIWNB | `mkx.DIWNB.DIWNB_HE` | 双视图：view1 = 原始属性空间（`AVFWNB`）；view2 的标签由 `KNNs_hard` 生成，再用 `AVFWNB`；`view_weight[2]` |
| PMWNB | `bayes.PMWNB.PMWNB.PMWNB` | 双基础视图（EWD 无监督离散化 10 bins + MDLP 有监督离散化）× 各 5 个子模型（base / SPODE-label / SPODE-prob / RF-label / RF-prob），两视图平均 |

### 需要说清楚的边界

**MAWNB 与 EMAWNB 共享同一套三视图架构**，同属 `weka.classifiers.zh.MVCAVWNB` 包：

- 视图构造方式相同（原始属性空间 / SPODE 标签空间 / RF 标签空间）；
- 区别在**融合**：MAWNB 固定 1/3 等权，EMAWNB 逐样本动态学权重；
- 区别在**内部规模**：MAWNB 的 SPODE / RF_m 是单实例，EMAWNB 是数组（集成）—— 这是两者模型体积差 6.7 倍（15.4 MB vs 103.5 MB）的原因。

所以准确的说法是：**六个算法互不相同，但 MAWNB 与 EMAWNB 是"同一架构的两个融合变体"，不是两套独立发明的算法。** 其余四个（A2WNB / CAVWNB / DIWNB / PMWNB）在视图构造层面就彼此不同。

### 顺带发现（未动）

1. **A2WNB 的第二阶段分类器是替身**。`A2WNB.java` 里 `m_Classifier2 = new weka.classifiers.bayes.WANBIA.WANBIA()`，但交付的源码包里没有 `WANBIA`，`backend/java/compat/WANBIA.java` 是 `extends NaiveBayes` 的占位类。也就是说 A2WNB 实际跑的是「RODE 属性增强 + NaiveBayes」，不是原设计的「RODE + WANBIA」。要恢复原设计需要 `WANBIA` 的真实源码。
2. **DIWNB 目录里有 3 个变体，只接了 1 个**。`DIWNB_HE` / `DIWNB_HL` / `DIWNB_S` 三个类都在源码里，但 `NbAlgorithmService.classNameFor()` 只映射了 `DIWNB_HE`；`KNNs_soft` 同样未被引用。
