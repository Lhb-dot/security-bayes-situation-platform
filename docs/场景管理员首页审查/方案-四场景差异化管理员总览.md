# 方案：四场景差异化「场景管理员总览」首页

> 本方案替代 [汇总-四场景结论与替代组件清单.md](汇总-四场景结论与替代组件清单.md) §4 的「四场景统一 8 块布局」。
> 上一版的问题：骨架完全相同 → 四个场景做出来会一模一样。本版改为 **共性底座（保证底线）+ 场景特色核心块（保证辨识度）**。
> 分场景组件级判定明细仍以四份分报告为准：[network.md](network.md) · [power.md](power.md) · [flight_deck.md](flight_deck.md) · [geological.md](geological.md)

---

## 1. 设计约束

| 约束 | 内容 |
|---|---|
| **C1 管理员总览** | 服务场景管理决策（数据资产、数据质量、建模覆盖、成员权限、流程积压水位），**不是**执行端/个人的研判辅助 |
| **C2 跨数据集共性** | 数字由该场景**多个数据集共同/合并**形成（合并总量、统一口径风险占比、各数据集在同一口径上的横向对比），**不是**某一个数据集内部的分布 |
| **C3 场景特色（本次新增）** | 四个场景的管理员首页必须能被一眼区分；特色必须来自该场景数据的**真实结构关系**，而不是换标题/换配色 |

**C3 的实现原则：特色块的选题 = 该场景数据集之间的结构关系。** 结构关系不同，管理员要管的事就不同，特色自然不同——不需要为了"不一样"而硬造差异。

## 2. 四场景的数据集结构关系（实测，C3 的选题依据）

实测来源：`tmp/_ds.txt`（`dataset` 表 21 行导出）+ ARFF 头部属性计数 + 文件哈希核验。

| 场景 | 管理员可见 | 不同标签语义 | 各数据集字段数 | **结构关系** | **特色主题** |
|---|---|---|---|---|---|
| **网络安全** | 3 份文件 / 3 个注册 | **2**（`Label{0,1}`、`class{normal,anomaly}`） | 41 / 41（字段数相同但**字段名完全不同**） | **双口径异构**：同一场景里两份数据说的"风险"不是同一件事 | **风险口径可比性** |
| **电力系统** | 2 份文件 / 2 个注册 | 1（`Target_Event{0,1}`） | 9 / 9（**同一物理文件副本**） | **同 schema 冗余**：唯一一个所有数据集共享同一字段结构的场景 | **数据集准入基线校验** |
| **舰面调度** | 4 份文件 / 2 个有效组 | 1（`Collision{0,1}`） | 279 / 279 / 281 / 279 | **同源多编码**：同一批 507 条样本的三种编码形态，冗余度最高 | **同源编码族治理** |
| **地质风险** | 6 份文件 / 6 个注册 | **5**（`Label`、`LS`、`landslides`、`landslide_size`、`class`） | 19 / 9 / 13 / 12 / 8 | **多角色异构家族**：因子表/标签表/致灾因子表/编目表/基线集各司其职 | **数据集角色分工与标签语义登记** |

**关键实测数字**（供方案与验收引用）：

- 网络：NF-UNSW 风险占比 **3.95%**（945/23897） vs KDD **46.61%**（3522/7556）→ **11.8 倍**差距，两套"风险"语言。
- 电力：可见 2 份文件 SHA256 **完全相同**（`4CB117BD…D1D6`）→ 字段级横向对比必然零偏离，真问题是"2 个注册 = 1 份数据"。
- 舰面：`carrier_feature2_biaoqian`(279) / `lisan`(279) / `paired_trail`(**281**，多 `PlaneID1`/`PlaneID2`) 为同批样本；`carrier_track_company_v1` 与 `lisan` 文件 MD5 相同（`77CB74B6…B6CD`）。
- 地质：5 种标签语义，其中 `dis_global_catalog` 的 `landslide_size` 是**多分类编目标签，不是风险标签**（不在 `DATASET_RISK_TYPES`），因此不产风险事件。

## 3. 共性底座（四场景一致，5 块）

底座只保证"管理员总览 + 跨数据集共性"的底线，不承担辨识度。

| 块 | 标题 | 组件 | 口径 | 数据来源 | 后端改动 |
|---|---|---|---|---|---|
| **S1** | 场景资产总览 KPI ×4 | `DashKpis` | ①有效数据集数（内容指纹去重）②有效样本总量（合并）③统一风险占比 ④**场景特色 KPI**（见 §4，四场景各不相同） | `dataset_count`/`dataset_file_count`/`sample_count`/`risk_count`/`risk_rate`（`dashboard_service.py:1068-1072`） | 无（需修根因：`_group_key`） |
| **S2** | 数据集资产明细 | `DashRows` | 每行一个数据集：样本量 · 标签字段 · 风险占比 · 字段数 · 可见性 · 已发布模型数 · 版本 | `datasets[]`（`:1073`）+ `getModelVersionList` 按 `dataset_logical_id` 归集 | `describe()` 补 `attribute_count`/`visibility` |
| **S3** | 建模覆盖（数据白躺检测） | `DashBars` | 每数据集：已发布 / 草稿 模型数 | 新增 `modeling:[{logical_id, published, draft}]` | **需新增聚合** |
| **S4** | 场景运行态水位 | `DashFunnel` + `DashKpis` + `DashLine` | 待处置积压 · 已处置率 · 处置漏斗 · 近 10 天活动趋势（场景级，`self_only=false`） | `get_workspace`（`:1298-1348`） | 无 |
| **S5** | 场景成员与权限 | `DashRows` | 成员数按角色分布 | `getUserList` 按 `scenario_id` | 无 |

> **S1 的第 4 个 KPI 刻意做成场景专属**——这是"底座"里唯一允许差异化的位置，让首屏第一眼就不同。

## 4. 四场景特色核心块（每场景 2 块，位置紧跟 KPI 之后）

特色块一律放在**第 2、3 屏位**（S1 之后、S2 之前），保证每个场景的"第一印象"不同。

---

### 4.1 网络安全 · 特色主题：风险口径可比性 + 统计维度覆盖缺口

**场景故事**：本场景有 3 份注册数据、2 套"风险"语言（`Label{0,1}` vs `class{normal,anomaly}`），风险占比相差 11.8 倍；6 张原图里有 4 张只有一份数据支撑。管理员要管的是「**这些数据能不能放在一起比**」。

#### D1「数据集风险口径可比性矩阵」`DashRows`（首选，醒目）

| 列 | 内容 |
|---|---|
| 数据集 | 展示名（`name`） |
| 标签字段 | `label_field` |
| 正类取值 | `DATASET_POSITIVE_LABELS[logical_id]` |
| 样本量 / 风险样本 | `record_count` / `risk_count` |
| 风险占比 | `risk_rate` |
| 与场景合并口径偏离 | `risk_rate ÷ 场景 risk_rate` 的倍数（标注「高 3.0×」「低 0.3×」） |
| 口径登记状态 | 是否在 `DATASET_RISK_TYPES` / `DATASET_POSITIVE_LABELS` 中登记（修好 `is_risk_label` 后即为 `is_risk_label`） |

- **C1**：直接指向管理动作——**统一或分档风险语言、决定哪些数据可合并训练**。
- **C2**：每行一个数据集，同一组口径并列，且末列由「场景合并口径」共同构成。
- **视觉锚点**：偏离倍数用色阶，11.8× 的差距一眼可见。
- **后端**：`describe()` 增 `positive_labels`（读 `DATASET_POSITIVE_LABELS`，1 行）+ `label_values`（复用 `label_stats` 已有的标签列计数，`:566-599`）。零新查询。

#### D2「流量统计维度覆盖矩阵」`DashRows`

行 = 5 个统计维度（协议 / 目的端口 / 包长分布 / 连接状态 / 应用服务），列 = 各数据集，格 = 有该字段 / 无。**实测**：NF 有端口+包长、无 `service`；KDD 有 `service`+`flag`、无端口包长 → 矩阵呈对角空白。

- **C1**：管理动作——补数据或砍指标；解释"为什么这些指标只能看一份数据"。
- **C2**：矩阵本身是跨数据集的字段存在性对比。
- **后端**：`describe()` 增 `field_names`（`fields_schema` 已在库），前端用常量 `NET_DIMENSIONS` 计算。零新查询。

#### 特色 KPI（S1 第 4 项）
**「风险口径分裂度」= 场景内不同标签语义数（实测 2）**，副标「2 套风险语言 · 不可直接合并」。

### 4.2 电力系统 · 特色主题：数据集准入基线校验（电参量 + 遥测链路）

**场景故事**：这是**唯一一个所有数据集共享同一字段结构（9 字段）的场景**，因此也是唯一能做**真正字段级跨数据集对比**的场景。管理员要管的是「**新数据集能不能达到电力基线**」——这是电力特有的入库门禁。

#### D1「电参量基线一致性（跨数据集）」`DashRows` + `DashColumns`

| 列 | 内容 | 电力基线（来自 `WorkspacePower.vue:18-23` 的 `NORMAL_BAND`） |
|---|---|---|
| 数据集 | 展示名 | — |
| 电压均值 | `VoltageLevel_kV` 均值 | 300 – 700 kV |
| 电流均值 | `CurrentAmp` 均值 | 400 – 1600 A |
| 温度均值 | `Temperature_C` 均值 | 30 – 90 ℃ |
| **工频合格率** | `PowerFrequencyHz ∈ [49.8, 50.2]` 的样本占比 | ≥ 99% |
| 遥测丢包率 | `Sensor_Packet_Loss_%` 均值 | ≤ 1% |
| 结论 | 达标 / 越界（越界列标红） | — |

- **C1**：数据集准入/退回的管理依据（不是"看看电流多大"的研判）。
- **C2**：每行一个数据集、同一字段同一口径横向对比——**且是本平台唯一字段级可比的场景**，这是电力独有的能力。
- **后端**：把 `_power_profile`（`:1147-1185`）从「单数据集」改为「遍历 `datasets`」，对 4 个白名单字段逐个求均值（复用 `_dataset_columns`/`_nums`/`_mean`）。白名单固定 4–5 个字段，不遍历全部 9 字段。
- **即时信号**：当前 2 个可见数据集为同一文件副本 → 本块会显示**两行完全一致**，直接暴露"2 个注册 = 1 份数据"。

#### D2「设备 × 系统 覆盖矩阵」`DashRows`

行 = 7 类 `Component`（Circuit Breaker / Transformer / Feeder / SCADA Unit / PMU / Voltage Regulator / Protective Relay）+ 4 类 `SystemName`，列 = 各数据集，格 = 样本量 + 故障率。

- **C1**：管理动作——哪类设备/系统缺数据、哪份数据能支撑哪类设备的建模。
- **C2**：矩阵由各数据集共同填充，暴露覆盖盲区。
- **后端**：遍历 `datasets` 统计 `Component`/`SystemName` 分布（同 D1 的改造）。

#### 特色 KPI（S1 第 4 项）
**「工频合格率」**（全场景合并口径，副标「49.8–50.2 Hz 区间占比」）——电力独有的电能质量门禁指标。

### 4.3 舰面调度 · 特色主题：同源编码族治理

**场景故事**：本场景是**唯一存在"同源多样本编码"的场景**——4 份可见文件其实是同一批 **507 条**样本的三种编码（数值连续版 279 字段 / Weka 离散区间版 279 字段 / 配对轨迹版 281 字段），有效组只有 2 个，冗余率 **50%**。管理员要管的是「**这些编码族该怎么治理**」。

#### D1「同源编码族治理表」`DashRows`（首选，醒目）

| 列 | 内容 |
|---|---|
| 数据集 | 展示名 |
| 同源组 | `groups[].group_id`（如 `carrier_shared_source`） |
| 编码形态 | 数值连续 / Weka 离散区间 / 配对轨迹（由字段类型判定：全 `numeric` → 数值；字段值为 `'(a-b]'` 区间串 → 离散；含 `PlaneID1/PlaneID2` → 配对） |
| 字段数 | `attribute_count`（**279 / 279 / 281**） |
| 样本量 / 正类 | `record_count` / `risk_count`（507 / 129） |
| 正类一致性 | 同源组内 `risk_count` 是否一致（一致 → 可安全只留一份） |
| 建模状态 | 该数据集已发布/草稿模型数 |

- **C1**：管理动作——**同源组只保留一份入模、统一编码规范**；解释"为什么 4 份数据只等于 2 个数据集"。
- **C2**：每行一个数据集，且"同源组/正类一致性"两列必须**跨数据集**才能算出。
- **后端**：`describe()` 增 `attribute_count`；编码形态由 `fields_schema` 类型判定；模型数走 S3 的 `modeling` 聚合。

#### D2「同源冗余度与去重收益」`DashKpis` + `DashBars`

- KPI：**同源冗余率 50%**（1 − 有效组数/文件数 = 1 − 2/4）、**去重前 1014 条 → 去重后 507 条**、**被同源吸收的数据集 2 份**。
- `DashBars`：各同源组的「文件数 vs 有效组数」对比。
- **C1**：管理动作——清理冗余注册、避免同一批样本重复训练/重复推理。
- **C2**：完全由 `groups[]`（`:1074-1082`）+ `dataset_file_count`/`dataset_count` 构成，是**零后端改动**块（修好 `_group_key` 后即准确）。
- **修好根因 3 后的直接效果**：页眉 1014 与卡片 507 的**自相矛盾消失**。

#### 特色 KPI（S1 第 4 项）
**「同源冗余率」**（副标「4 份文件 → 2 个有效数据集」）。

### 4.4 地质风险 · 特色主题：数据集角色分工与标签语义登记

**场景故事**：本场景有 **6 份可见数据、5 种字段结构（19/9/13/12/8）、5 种标签语义**，是四场景中最庞大的异构数据集家族：因子表、标签表、致灾因子表、全球编目表、随机基线集各司其职，其中编目表的 `landslide_size` **不是风险标签**，因此不产风险事件。管理员要管的是「**每份数据到底承担什么角色**」。

#### D1「数据集角色分工矩阵」`DashRows`（首选，醒目）

| 列 | 内容 |
|---|---|
| 数据集 | 展示名 |
| **角色** | 因子表 / 风险标签表 / 致灾因子表 / 全球编目表 / 随机基线集（按 `logical_id` 常量映射） |
| 字段数 | `attribute_count`（19 / 9 / 13 / 12 / 8） |
| 标签语义 | `label_field`（`Label` / `LS` / `landslides` / `landslide_size` / `class`） |
| 标签类型 | 二分类 / 多分类编目 / 计数型（`landslides` 为 0–9,11 的数值） |
| 参与训练 | 该数据集是否存在 `ModelVersion` |
| 产生风险事件 | `is_risk_label`（编目表为 false） |
| 样本量 / 风险占比 | `record_count` / `risk_rate` |

- **C1**：管理动作——**哪些数据白躺（有数据无模型）、为什么编目数据不产事件、标签语义是否登记**。
- **C2**：每行一个数据集，且"参与训练/产生事件"两列是跨数据集的一致性核对。
- **后端**：`describe()` 增 `attribute_count` + `label_kind`；角色由前端常量映射；"参与训练"走 `getModelVersionList`。零新查询。

#### D2「地形因子跨数据集覆盖矩阵」`DashRows`

行 = 8 个地形因子（`Lithology` / `Landuse` / `Aspect` / `Slope` / `EVI` / `Elevation` / `Roughness` / `Slope_roughness`），列 = `dis_raw_data` / `dis_landslides` / `dis_causative_factors`，格 = 覆盖 + **离散化区间是否一致**（实测 `Slope` 在三份中的分箱边界各不相同）。

- **C1**：管理动作——因子口径统一、判断模型能否跨数据集迁移。
- **C2**：矩阵由多份数据集共同填充；"区间是否一致"天然是跨数据集比对。
- **后端**：只用 `fields_schema` 的字段名与取值定义，**不做数值解析**（规避现有 `_mid_of_interval` 把 Weka 区间串取端点当均值的问题）。

#### 特色 KPI（S1 第 4 项）
**「未建模数据集数」**（副标「6 份数据中 N 份无模型」，实测 ≥3）——直接量化"数据白躺"。

## 8. 验收标准

改造完成后，用以下 5 条验收：

1. **C1**：每个组件都能回答"管理员据此做什么决定"；页面上不出现"我的待处置告警""最近告警""关键因子贡献排行"等执行端组件。
2. **C2**：随机点开任一组件，追到后端，其数字**不能**只来自一个硬编码 `logical_id`；至少每行/每片/每序列对应一个数据集，或为场景合并口径。
3. **C3-1 结构辨识**：把四个页面截图去色后，仅看**标题与图型**能区分出是哪个场景。
4. **C3-2 无重复特色块**：四个场景的 D1/D2 互不相同，且每个 D 块都能追溯到该场景的数据集结构关系。
5. **数据自洽**：页眉 `sample_count` 与卡片数字**不再矛盾**（P0 修好后）；`dataset_file_count` 与 `dataset_count` 的差额能在「同源冗余」块里被解释。
