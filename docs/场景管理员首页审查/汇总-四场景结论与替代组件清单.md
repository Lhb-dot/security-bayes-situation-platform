# 场景管理员首页审查 · 四场景汇总（组件判定 + 替代组件清单）

- 审查对象：`/scenarios/:scenarioId/dashboard` → `AdminProfilePage.vue` → `Profile{Network,Power,Flightdeck,Geological}.vue`
- 数据接口：`GET /api/v1/dashboard/scenarios/{id}/profile` → `dashboard_service.get_profile`（`dashboard_service.py:1038-1094`）+ 四个 `_*_profile` 场景聚合函数
- 对照物（普通用户首页）：`Workspace{Network,Power,Flightdeck,Geological}.vue`（`GET /workspace`，`dashboard_service.py:1298-1348`）
- 分场景明细报告：[network.md](network.md) · [power.md](power.md) · [flight_deck.md](flight_deck.md) · [geological.md](geological.md)
- 本汇总为只读调查结论，**未修改任何 `.vue` / `.py` / `.ts` / 数据库**。

## 0. 判定标准（用户原话拆解）

| 代号 | 含义 | 判定方式 |
|---|---|---|
| **C1 管理员总览视角** | 服务「场景管理员管好这个场景」：数据资产、数据质量、建模覆盖、成员权限、流程积压水位；**不是**执行端/个人的研判辅助 | 是否指向管理动作。执行端派活清单（待处置告警清单）、单条事件明细、研判特征统计 → 不满足 |
| **C2 跨数据集共性口径** | 数字由该场景**多个数据集共同/合并**形成（合并总量、统一口径风险占比、各数据集在同一口径上的横向对比）；**不是**某一个数据集内部的分布 | **追到后端**：只读某一个硬编码 `logical_id` → 不满足；每行一个数据集、口径统一 → 满足 |

组件级结论规则：C1、C2 都满足 → **满足**；一项满足另一项部分满足，或两项都部分满足 → **部分满足**；其余 → **不满足**。
计数口径：每个 `DashKpis` 指标块算 1 个组件，每个 `DashCard` 算 1 个组件（舰面另单列 1 条页眉口径）。

## 2. 五个跨场景共性根因（全部有代码/文件证据）

### 根因 1 · 画像接口按硬编码 `logical_id` 取单一数据集（C2 直接死因）

| 场景 | 硬编码位置 | 后果 |
|---|---|---|
| network | `dashboard_service.py:1103` `by_logical.get("nf_unsw_nb15_v2")`、`:1104` `get("kdd_train_20_percent")` | 6 张图只消费这两个 key；`net_flow_company_v1`（company，管理员可见）及**任何后续新上传数据集**在 6 张图里零出现 |
| power | `dashboard_service.py:1150` `by_logical.get("powergrid_knowledgebase")` | 11/12 个组件的字段 100% 来自这一份 ARFF（`:1176-1184`）；`power_grid_company_v1` 被丢弃 |
| flight_deck | `dashboard_service.py:1190` `by_logical.get(CARRIER_CANONICAL)`（`CARRIER_CANONICAL="carrier_feature2_biaoqian"`，`:106`） | 函数全部返回值出自一份数据集，响应自述 `sources.dataset`（`:1256-1259`）；可见 4 份中 id7/id8/id18 全不可见 |
| geological | `dashboard_service.py:1265` `get("dis_raw_data")`、`:1274-1282` `dis_global_catalog` | `dis_landslides`/`dis_causative_factors`/`dis_guaruja_random` 只当列表行，字段级聚合从未读取 |

**这解释了用户观察到的现象**：管理员上传一个新数据集，首页除「数据集规模对比」多一根柱子外**毫无变化**。

### 根因 2 · 现成的跨数据集结构被前端弃用

`get_profile` 已经下发了「每数据集一行、口径统一」的结构，但三个场景完全没用：

| 字段 | 位置 | network | power | flight_deck | geological |
|---|---|---|---|---|---|
| `ProfileBase.datasets[]`（`record_count/risk_count/risk_rate/label_field/is_risk_label/version`） | `dashboard_service.py:1073`、`describe:618-631` | 仅用于 1 张图 | **0 次** | **0 次** | 用于 4 张图 |
| `ProfileBase.groups[]`（同源分组、`deduplicated`） | `:1074-1082` | 0 次 | **0 次** | **0 次** | 0 次 |
| `sample_count/risk_count/risk_rate` | `:1070-1072` | 做成 3 个 KPI | 1 个 KPI | 1 个 KPI | **只在副标题**（`AdminProfilePage.vue:46`） |

### 根因 3 · 同源去重只覆盖航母三份 → 合并口径是重复计数

`_group_key`（`dashboard_service.py:634-636`）仅当 `logical_id ∈ CARRIER_LOGICAL_IDS`（`:100-104`）才归组；其余场景的「同一份物理文件、多个 logical_id」被当成多个数据集求和。

**独立复现的哈希证据（本次核验）**：

| 场景 | 平台版 | 后上传版 | MD5/SHA256 | 结论 |
|---|---|---|---|---|
| network | `data/network/NF-UNSW-NB15-v2.arff` | `data/network_security/NF-UNSW-NB15-v2.arff` | MD5 `ACE14B10…BA67` **相同** | 同源未去重 |
| network | `data/network/KDDTrain_20Percent.arff` | `data/network_security/KDDTrain_20Percent.arff` | MD5 `734AA903…31DC` **相同** | 同源未去重 |
| power | `data/power/powergrid_knowledgebase_dataset.arff` | `data/power_system/powergrid_knowledgebase_dataset.arff` | SHA256 `4CB117BD…D1D6` **相同** | 同源未去重 |
| flight_deck | `data/carrier/Feature2_Cleaning_lisan.arff` | `data/flightdeck_operation/Feature2_Cleaning_lisan.arff` | MD5 `77CB74B6…B6CD` **相同** | 同源未去重 |
| geological | `data/geological/DIS_Landslides.arff` | `data/geological_risk/DIS_Landslides.arff` | MD5 `0536D11C…26B8` **相同** | 同源未去重 |
| geological | `data/geological/DIS_raw_data.arff` | `data/geological_risk/DIS_raw_data.arff` | MD5 `F130D035…C8E4` **相同** | 同源未去重 |
| flight_deck（已去重） | `data/carrier/Feature2_Cleaning_biaoqian.arff` | `data/carrier/paired_TrailData_feature2_biaoqian.arff` | MD5 不同但数值列逐行相同 | 白名单内，已归组 |

**后果（实测数字）**：

- network：管理员看到 `sample_count=55350` / `risk_rate=9.78%`，按内容去重应为 **31453 / 14.20%**（虚高 76%）；`ProfileNetwork.vue:32` 副标题还写死「两数据集合计」，实际 `dataset_count=3`。
- power：`powergrid_knowledgebase` 与 `power_grid_company_v1` 同为 2013 行同源文件被求和 → 管理员看到约 4000 条，实际约 2000 条。
- flight_deck：管理员看到 `sample_count=1014`（507×2），而**所有卡片数字都基于 507**（`collision_count=129`）→ **同一页页眉与卡片自相矛盾**。

### 根因 4 · `DATASET_RISK_TYPES` / `DATASET_POSITIVE_LABELS` 白名单不含后上传数据集

`describe()` 的 `is_risk_label` = `dataset.logical_id in DATASET_RISK_TYPES`（`dashboard_service.py:627`），而 `constants.py:308-319` 只登记了 10 个历史 `logical_id`。生产 seed 上传的 `net_flow_company_v1` / `power_grid_company_v1` / `carrier_track_company_v1` / `geo_slope_company_v1` 及对应 personal 版本**全部不在白名单** → `is_risk_label=false`。

后果：`ProfileGeological.vue:42` 的 `riskDatasets()` 用该标志过滤，**静默丢弃 `geo_slope_company_v1`**（一份 `LS` 标签的滑坡数据被判成「非风险标签」）；舰面同样把一份 `Collision` 标签数据判成非风险标签。

### 根因 5 · CSV 数据集样本量恒为 0

`_DatasetReader.rows` 只走 `read_arff`（`dashboard_service.py:534`），`label_stats` 在无表头时直接记 0（`:585-588`）；而上传侧支持 CSV（`dataset_service.py:350-352`、`utils/dataset_file_reader.py:41`）。`data/power_system/sample_demo.csv` 即此类上传留下的孤儿文件。

### 附带发现

- `docs/首页字段口径说明.md` 被代码四处引用（`AdminProfilePage.vue:4`、`ProfileFlightdeck.vue:4`、`dashboard_service.py:4,10,900`）但**仓库中不存在**，所有「字段口径」注释处于无据可查状态。
- **数据集内特征结构互不相容**（本次核验 ARFF 头部）：NF-UNSW 用 `L4_DST_PORT/PROTOCOL/IN_BYTES`，KDD 用 `duration/protocol_type/service/flag/src_bytes`，端口与包长在 KDD 中**根本不存在**；carrier 有 279 个属性、powergrid 只有 9 个；`DIS_raw_data` 与 `DIS_Landslides` 因子列名与离散化区间各不相同。**因此「共性统计」只能建立在元数据 + 统一标签/风险语义维度上，不可能靠合并特征分布实现**——这正是替代方案必须走「数据集 × 治理维度」的原因。

## 4. 替代组件清单（统一范式）

> **本节已被 [方案-四场景差异化管理员总览.md](方案-四场景差异化管理员总览.md) 取代。**
> 本节给出的是「四场景共用一套骨架」的统一范式，会导致四个场景做成一模一样；新方案改为「共性底座 5 块 + 场景特色核心块 2 块」，特色来自各场景真实的数据集结构关系。本节保留作为替代组件的**候选池**（§4.3 的逐组件对照仍然有效）。

### 4.1 替代原则

> **把「某一个数据集内部的字段分布」换成「以数据集为行/片/序列的治理维度横向对比 + 全场景合并口径」**，即用户所说的「这个场景下数据集共同体现一种统计」。

数据支撑的两条铁律（已核验）：

1. 场景内各数据集**特征结构互不相容**（端口/包长在 KDD 中不存在；279 vs 9 个属性），所以不能靠合并特征分布造「共性」。
2. 场景内所有数据集**共享同一套风险语义**（`DATASET_RISK_TYPES` 把它们映射到同一个 `RISK_TYPE_*`，`is_risk_label`/`_label_is_risk` 给出统一正类判定）——**这才是场景级「共性统计」的合法基础**。

### 4.2 建议的标准布局（四场景统一，一屏管理员总览）
