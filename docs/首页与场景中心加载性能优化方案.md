## 一、结论先行

首页与场景中心的卡顿**不是网络问题，也不是前端渲染问题，而是后端每次请求都重新全量解析 ARFF 文件**。

实测（同一台机器、服务已预热、连续多次调用）：

| 接口 | 页面 | 实测耗时 | 其中 ARFF 解析 | 其中 DB + 聚合 |
|---|---|---|---|---|
| `GET /api/v1/dashboard/admin/overview` | 平台运行总览（首页） | **1.21s** | 1.11s（9 个文件） | 0.10s |
| `GET /api/v1/scenarios/overview` | 场景中心 | **1.25s** | 1.21s（9 个文件） | 0.04s |
| `GET /api/v1/dashboard/scenarios/1/profile` | 场景数据画像（网络） | 0.76s | 主要耗时 | 少量 |
| `GET /api/v1/dashboard/scenarios/3/profile` | 场景数据画像（甲板） | 0.70s | 主要耗时 | 少量 |
| `GET /api/v1/dashboard/scenarios/4/profile` | 场景数据画像（地质） | 0.48s | 主要耗时 | 少量 |
| `GET /api/v1/dashboard/scenarios/2/profile` | 场景数据画像（电力） | 0.04s | — | 少量 |

**关键证据：连续调用第二次依然一样慢**（首页 1.21s → 1.26s，场景中心 1.25s → 1.19s），说明当前**完全没有任何跨请求缓存**，每次刷新页面都要把约 15MB 的 ARFF 重新逐字符解析一遍。

单文件最贵的是 `data/network/NF-UNSW-NB15-v2.arff`（3.3MB / 23897 行），单次解析 **0.44 ~ 0.52s**，占掉半个页面。

### 排查中已排除的方向

- **响应体过大 / 缺压缩**：不是。三个接口的 JSON 实际只有 1.6 KB ~ 5.7 KB，gzip 后 0.5 ~ 1.3 KB，压缩收益可忽略。后端确实没挂 `GZipMiddleware`，但即使挂了也几乎看不出差别，**不建议优先做**。
- **数据库慢**：不是。整个 DB 只有 4 个场景 / 11 个数据集 / 11 条推理记录，DB + 内存聚合合计仅 0.04 ~ 0.10s。
- **Java 推理服务**：与本链路无关。

## 二、根因定位

### 2.1 缓存的生命周期是「一次请求」，不是「一个进程」

`backend/app/services/dashboard_service.py:304`

```python
class _DatasetReader:
    """按会话缓存 ARFF 读取结果，避免同一份文件在一次请求内被重复解析。"""

    def __init__(self) -> None:
        self._cache: dict[int, tuple[list[dict], list[list[str]]]] = {}
        self._counts: dict[int, int] = {}
```

注释本身写得很清楚——**只保证"一次请求内"不重复解析**。而它在每个请求里都被重新 new 一次：

- `dashboard_service.py:495`（`get_admin_overview`，首页）
- `dashboard_service.py:666`（`get_scenario_overview`，场景中心）
- `dashboard_service.py:745`（`get_profile`，场景画像）
- `dashboard_service.py:1195`（`get_workspace`，我的工作台）

所以首页每次加载 = 重新解析 9 个文件 ≈ 1.1s，且不随用户数、并发数变化，**永远是 1.1s**。

### 2.2 为了数一列标签，把整张表全物化了

`dashboard_service.py:323` 的 `label_stats` 只想要两个数字：总行数、风险行数。

```python
def label_stats(self, dataset: Dataset) -> tuple[int, int]:
    fields, rows = self.rows(dataset)          # ← 全量物化所有列、所有行
    if not fields:
        return 0, 0
    index = _field_index(fields).get(_clean(dataset.label_field))
    return len(rows), sum(1 for value in _raw_values(rows, index) if _label_is_risk(value))
```

而 `self.rows()` 调的是 `read_arff(path, max_rows=None)`（`app/utils/arff_reader.py:84`），它会：

1. 把整个文件逐行读进来；
2. 对每一行调用 `_split_data_row()`——一个**手写的逐字符状态机**（`arff_reader.py:53`），为了处理引号内逗号，`for` 循环 + 字符串拼接；
3. 把每个单元格都建成独立的 Python `str` 对象，存进 `rows: list[list[str]]`；
4. 额外还顺手采集 `sample_values`（标签统计根本用不到）。

结果是：**为了得到 23897 行里标签列的 945 个正样本，创建了约 120 万个字符串对象。**

### 2.3 量化对比

用「只统计标签列」的写法（`str.split(",")` 走 C 实现 + 只取末列）跑同样 11 个文件：

## 三、优化方案（按投入产出比排序）

### P0-1　把缓存从「请求级」提到「进程级」　（改动最小，收益最大）

**位置**：`dashboard_service.py:304`

把 `_cache` / `_counts` 从实例属性改成模块级字典，key 用 `(dataset.id, os.path.getmtime(path), os.path.getsize(path))`，这样文件被替换时会自动失效。

**注意内存**：不建议直接缓存全量 `rows`。按现在 11 个文件约 5.2 万行 × 几十列估算，常驻内存可能到数百 MB 量级。**建议只缓存聚合结果**，例如：

```python
# 模块级，进程内共享
_LABEL_STATS_CACHE: dict[int, tuple[float, int, int, int]] = {}
# dataset_id -> (file_mtime, file_size, total_rows, risk_rows)
```

配合 P0-2 一起做，缓存的对象本身就很小。

**风险**：多 uvicorn worker 部署时每个进程各有一份缓存（不共享）。当前单进程开发环境下没有影响；上多 worker 时再考虑 Redis。

### P0-2　只统计标签列，不再全量解析　（根治解析开销）

**位置**：`app/utils/arff_reader.py`

新增一个轻量函数，只做「数标签列」这一件事：

```python
def count_arff_label(path: str, label_index: int) -> tuple[int, int]:
    """只统计指定列的行数与正类数，不物化其它列。"""
```

实现要点：

- 用 `csv.reader` 替代手写的 `_split_data_row` 状态机。`csv.reader` 是 C 实现，且能正确处理引号内逗号，比 `str.split` 更安全。
- **必须加一致性校验**：读第一行数据时比对字段数是否等于 `@ATTRIBUTE` 的个数，不一致就回退到现有 `read_arff` 实现。ARFF 的引号规则与 CSV 并非完全一致（ARFF 常见单引号、枚举值可能不带引号），不能盲目假设两者等价。
- 保留现有 `read_arff` 不动——数据集预览、字段样例值（`sample_values`）这些场景仍然需要全量解析，只是首页/场景中心不再走它。

**收益**：解析 1.83s → 0.080s（23x）。首次加载 1.21s → 0.18s。

### P0-3　聚合结果预计算落库　（长期方案，数据量继续增长时再做）

在数据集登记 / 回填时，把 `record_count`、`risk_count` 以及各场景画像需要的字段统计写入一张 `dataset_stat` 表（或在 `dataset` 表上加列）。

- 页面接口退化成几条带索引的 `SELECT`，稳定在毫秒级；
- 与文件大小彻底解耦，以后换更大的数据集也不会变慢；
- 失效策略：表里同时存 `file_mtime` + `file_size`，读取时校验，不一致就重算并回写（懒加载，不用做定时任务）。

### P1-1　消除循环内的 N+1 查询

**位置**：`dashboard_service.py:534-553`

`get_admin_overview` 在每个场景的循环体里跑了 3 次 `self.db.scalar(select(func.count())...)`。4 个场景就是 12 次额外往返。同文件的 `get_scenario_overview`（`:659`）已经用了正确写法——一次 `group_by` 查出所有场景的计数再查表：

```python
published_rows = self.db.execute(
    select(ModelVersion.scenario_id, func.count())
    .where(ModelVersion.status == MODEL_STATUS_PUBLISHED)
    .group_by(ModelVersion.scenario_id)
).all()
published_by_scenario = {scenario_id: count for scenario_id, count in published_rows}
```

把 `get_admin_overview` 对齐成同样的模式即可。收益约 0.1s，且**场景数增加时不会线性变差**。

### P1-2　去掉重复计算

**位置**：`dashboard_service.py:505` 与 `:520`

`_effective_counts(reader, datasets)` 先对全量数据集算了一遍（505 行），紧接着又在每个场景循环里对子集再算一遍（520 行）。应改成：先按 `scenario_id` 分组算一次，全局值由各场景累加得到，避免重复遍历。

### P1-3　鉴权依赖里每次请求都写库

**位置**：`app/api/deps.py:57`

```python
session.last_seen_at = now
db.commit()
```

每个 API 请求（含 GET）都会触发一次 `UPDATE auth_session` + `COMMIT`。首页一次加载就有 2~3 个请求，等于多出 2~3 次写事务。

建议：距上次 `last_seen_at` 超过 60 秒才写，或把这个更新挪到后台/登录态续期逻辑里。

### P1-4　给聚合接口加 HTTP 缓存

这三个接口的数据来自静态数据集，变化频率极低（只在有人上传/训练/推理时变）。可以：

- 返回 `ETag`（内容哈希）+ `Cache-Control: private, max-age=30`，浏览器重复导航直接走 304；
- 或服务端加一层 `TTLCache(ttl=30~60)`，响应头带 `X-Cache: HIT/MISS` 方便排查。

注意：如果按角色返回不同内容（`get_scenario_overview` 就是按角色收窄可见范围的），缓存 key 必须带上 `user_id` / `role` / `scenario_id`，**且 `Cache-Control` 必须是 `private`**，不能是 `public`。

### P2-1　首屏不要等 `/auth/me`

**位置**：`frontend/src/main.ts`

```ts
userStore.bootstrap().finally(() => app.mount('#app'));
```

现在整个 Vue 应用**要等一个鉴权接口往返完成才挂载**，这段时间是纯白屏。建议改为立即 `app.mount()`，把 `bootstrap()` 的结果交给路由守卫 `await`（`router/guards.ts` 里本来就在读 `userStore.currentUser`，改成异步等待即可），期间显示骨架屏。

### P2-2　`RiskAnalysis` 从入口包剥离

**位置**：`frontend/src/router/index.ts:6`

```ts
import RiskAnalysis from '@/views/Model/RiskAnalysis.vue';   // ← 唯一一个静态 import
```

其余 14 条路由全是 `() => import(...)` 懒加载，只有这一个（897 行的训练预测页）被打进了入口 chunk。改成懒加载即可。

### P2-3　Element Plus 按需引入

**位置**：`frontend/src/main.ts`

```ts
import ElementPlus from 'element-plus';
import 'element-plus/dist/index.css';
app.use(pinia).use(router).use(ElementPlus);
```

全量引入的代价（实测构建产物）：

- 入口 JS chunk：**979 KB**
- 入口 CSS：**381 KB**
- Vite dev 预构建的 `element-plus.js`：**1.9 MB**（未压缩）

改用 `unplugin-vue-components` + `unplugin-auto-import` 按需引入，只打包实际用到的组件。这是首屏可交互时间下降最明显的一项。

### P2-4　客户端加一层 TTL 缓存 + 并发去重

**位置**：`frontend/src/utils/request.js`

现状：场景中心 → 场景大屏 → 返回场景中心，**每次导航都重新请求一遍**，1.2s 的等待要重复吃。

在 `request.js` 里加一个针对 GET 的短 TTL 缓存（30~60s）+ in-flight 请求去重（同一 URL 并发只发一次），返回列表页就能秒开。项目里 `scenarioApi.ts:100` 的 `_idByCodeCache` 已经是这个思路，扩展到聚合接口即可。

写操作（POST/PUT/PATCH/DELETE）成功后清掉相关缓存。

### P2-5　场景大屏首次进入少一次往返

**位置**：`views/Model/ScenarioCenter.vue:40` + `api/scenarioApi.ts:106`

场景卡片接口 `/scenarios/overview` 返回的 `ApiScenarioOverviewCard` **已经带了数字 `scenario_id`**，但 `toScenarioCard()` 把它丢掉了，前端改用 `code` 作路由参数，于是进入大屏时 `getScenarioProfile(code)` 又要先调 `resolveScenarioId()` → 命中不了 `_idByCodeCache` 就多发一次 `/api/v1/scenarios`。

**两次串行请求**。建议路由直接带数字 id，或在场景中心跳转前就预热 `_idByCodeCache`。

### P2-6　骨架屏替代全页 spinner

**位置**：`components/dashboard/DashShell.vue`

现在是 `v-if="data"` —— 数据没回来之前整个内容区只有转圈，用户感知到的等待时间 = 完整接口耗时。建议：

- 页面框架、标题、卡片边框、KPI 占位先渲染（骨架屏）；
- 数据到达后填入；
- 图表类组件用 `requestIdleCallback` 或分批渲染，避免数据一到就同时初始化 6 个 ECharts 实例造成主线程卡顿。

> 注：`components/charts/EChartBase.vue` 已经做了 `echarts/core` + `use([...])` 的按需注册，这块写法是对的，不需要改。

### P3-1　开发环境本身也是「卡顿」的一部分

`start_all.ps1:179` 用的是 `npm run dev`。Vite dev 模式下：

- 依赖不压缩：`element-plus.js` 1.9 MB + `echarts_charts.js` 0.59 MB + `echarts_components.js` 0.57 MB + 其余，**首次打开要拉约 3.5 MB 未压缩 JS**；
- 应用代码按模块逐文件请求（几百个 HTTP 请求）。

**建议**：演示、验收、答辩场景改用 `npm run build && npm run preview`（或直接托管 `dist/`）。生产构建下入口只有 979 KB minified，其余页面走懒加载分块。

### P3-2　固定依赖预构建范围

**位置**：`frontend/vite.config.ts`

```ts
optimizeDeps: {
  include: ['element-plus', 'echarts/core', 'echarts/charts', 'echarts/components', 'echarts/renderers'],
}
```

避免开发过程中 Vite 中途发现新依赖、触发重新预构建并整页 reload（用户体感上就是「突然卡住然后白一下」）。

## 四、建议落地顺序

| 步骤 | 内容 | 预期效果 | 改动范围 |
|---|---|---|---|
| 1 | P0-2 只统计标签列 + P0-1 结果缓存 | 首次 1.21s → **0.18s**，之后 → **0.10s** | `arff_reader.py`、`dashboard_service.py` |
| 2 | P2-1 首屏不等鉴权、P2-2 路由懒加载、P2-3 Element Plus 按需 | 白屏时间显著缩短，入口包体积下降 | `main.ts`、`router/index.ts`、`vite.config.ts` |
| 3 | P1-1 分组查询、P1-2 去重、P1-3 鉴权写库、P1-4 ETag | 再省 0.1~0.2s，且场景数增长后不退化 | `dashboard_service.py`、`deps.py` |
| 4 | P2-4 客户端缓存、P2-5 减少一次往返、P2-6 骨架屏 | 二次访问体感接近瞬时 | `request.js`、`ScenarioCenter.vue`、`DashShell.vue` |
| 5 | P0-3 聚合结果落库 | 毫秒级，与文件大小解耦 | 新增表 + 数据集登记链路 |

**第 1 步做完就能解决绝大部分问题**，且改动集中在一个文件的两个函数，回归风险最低。

## 四·补二　第二轮实施记录（同日续做）

### 1. 场景画像聚合热路径（`_num` 快路径）

cProfile 显示 `_network_profile` 单请求会调用 `_num` **16.7 万次**、`_clean` **23 万次**、`str.strip` **200 万次**。原因：数值列里绝大多数单元格是「首尾无引号无空白的数字字符串」，却仍要走 `_clean()` 的三次 strip + `lower()` 再 `float()`。

改动：`_num()` 增加快路径 —— 首尾字符都不在 `_QUOTES` 中时直接 `float()`，失败再落回慢路径。

**等价性验证**：以 11 个数据集的**全部真实单元格（1,954,272 个）** + 70 个边界用例（`nan` / `inf` / `-inf` / `Infinity` / `1_000` / `.5` / `12.` / `(a-b]` 区间串 / 带引号 / 带空白 / 缺失值 / 非数值 等）逐个比对，**0 处不一致**；NaN 泄漏数量新旧相同（`float('nan')` 入参时两版都返回 NaN，属既有行为）。

效果：`_num` 吞吐 1.14x；画像耗时 network 150ms → **118ms**、geological 121ms → **102ms**。

> 附带记录一个**失败尝试**：给 `_clean()` 加「首尾无引号则跳过 strip」的快路径后，实测**反而慢 0.85x** —— CPython 的 `str.strip()` 在无需裁剪时会原样返回，比额外的下标判断更便宜。已回退，回退后画像还更快（118ms vs 126ms）。

### 2. Element Plus 按需引入（P2-3）

先确认依赖面：全项目**未使用任何 Element Plus 指令**（无 `v-loading`），服务式调用只有 `ElMessage`（105 处）与 `ElMessageBox`（2 处）。

- `vite.config.ts`：新增 `unplugin-auto-import` + `unplugin-vue-components`（`ElementPlusResolver`）；新增 `optimizeDeps.include` 固定预构建范围，避免开发中途重新预构建触发整页 reload。
- `main.ts`：移除 `app.use(ElementPlus)` 与全量 `element-plus/dist/index.css`；改为显式引入 `theme-chalk/base.css` + `el-message.css` + `el-message-box.css`。
  **这一步是必须的** —— `ElMessage`/`ElMessageBox` 在 11 个文件里是显式 import，不会被 AutoImport 接管，样式也不会自动注入，漏了就会变成无样式裸文本。

效果：入口 JS 968.3 KB → **81.8 KB**、入口 CSS 372.4 KB → **34.8 KB**，首屏合计 1468 KB → **241.9 KB（6.07x）**。

### 3. 顺带修掉一个阻塞性问题：12312 的静态站点从未可用

排查生产构建时发现：`main.py` 的 `WEB_DIR` 指向的是 **`frontend/` 源码目录**，返回的是 Vite **dev 版** `index.html`（引用 `/src/main.ts`）。浏览器无法执行 `.ts`，且 Windows 上 `mimetypes` 会把 `.ts` 识别成 `video/vnd.dlna.mpeg-tts`，直接触发模块脚本 MIME 校验失败 —— 即 `http://localhost:12312/` 打开必然白屏。

改动：新增 `SITE_DIR`，优先挂 `frontend/dist`（存在 `dist/index.html` 时），否则回退原行为。`app.mount("/", StaticFiles(directory=str(SITE_DIR), html=True))`。

效果：`npm run build` 之后，**单端口 12312 即可访问完整站点**，不必再依赖 5173 的 Vite dev server。

> 遗留（未动）：`main.py:1962` 有一行 `return FileResponse(str(WEB_DIR / "index.html"))` 因上方装饰器/函数定义被注释掉，被 Python 解析成了 `_is_strategic()`（定义于 1160 行）的末尾语句。属既有代码问题，与本次性能任务无关，**未擅自修改**。

## 六、本次实测方法（可复现）

1. **服务层直接计时**：在进程内构造 `DashboardService(db)`，分别调用 `get_admin_overview` / `get_scenario_overview` / `get_profile`，`perf_counter` 计时。
2. **耗时拆分**：monkeypatch `dashboard_service.read_arff` 与 `count_arff_rows` 统计调用次数与累计耗时，用总耗时相减得出 DB + 聚合部分。
3. **解析方案对比**：对 11 个 ARFF 分别跑「`read_arff` 全量」与「只统计末列」，对比耗时。
4. **响应体体积**：对服务层返回值 `json.dumps` 后统计原始字节与 gzip 后字节。
5. **响应头**：`curl -D -` 检查是否存在 `content-encoding: gzip`。
6. **前端体积**：读取 `frontend/dist/assets` 与 `frontend/node_modules/.vite/deps` 的文件大小。
