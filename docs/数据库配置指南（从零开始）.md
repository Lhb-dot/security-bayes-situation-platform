# 数据库配置指南（从零开始）

> 适用对象：拿到本项目代码、需要在一台**全新环境**上把数据库配起来的人。
> 本文从零开始，只讲"数据库怎么跑起来"，不涉及业务功能开发。
> 数据文件（ARFF 数据集）不属于本文范围，见文末《补充：与数据文件的关系》。

---

## 0. 先说结论（TL;DR）

一条命令启动数据库，两个命令初始化表和数据：

```bash
# 1. 启动 PostgreSQL（根目录）
docker compose up -d

# 2. 建表 + 写入场景/算法基础数据（backend 目录）
cd backend
python -m alembic upgrade head

# 3. 注册测试账号 + 登记数据集 + 写入风险阈值（项目根目录）
python ../scripts/seed_test_data.py --skip-copy
```

> 前提：已装 Docker Desktop（WSL2 后端）、`data/` 目录下已有 ARFF 数据文件、`backend/app/.env` 已按第 5 节创建。
> 第 3 步的 `--skip-copy` 表示 ARFF 已在 `data/` 下、只登记数据库；若源文件在别处可去掉该参数（会自动拷贝）。

---

## 1. 数据库在本项目里的角色

本项目使用 **PostgreSQL 16** 作为唯一数据库（无 SQLite / 无其它数据库）。它存放全部**业务元数据**：

- **12 张业务表**：用户、场景、数据集、算法、模型版本、风险阈值、推理记录、风险事件、报告等（对应 `docs/数据库设计文档v2.md`）
- **表结构**由 SQLAlchemy ORM 模型（`backend/app/models/`）+ Alembic 迁移（`backend/alembic/versions/`）管理

数据文件（`data/` 下的 ARFF 等）**不存数据库**，数据库只登记它们的路径（`datasets.file_path`，相对路径）与字段结构。

## 2. 准备阶段（仅第一次做）

### 2.1 Docker Desktop（含 WSL2）

- Windows：安装 **Docker Desktop**，Settings → General 勾选 **Use the WSL 2 based engine**
- 确认可用：

```bash
docker --version
docker compose version
```

### 2.2 拉取 PostgreSQL 镜像

镜像 `postgres:16` 需要从 Docker Hub 拉取，**网络受限时需先开代理/梯子**（镜像拉不动是本项目最常见的首次卡点）：

```bash
docker pull postgres:16
```

---

## 3. 方式 A：Docker 一键启动（推荐）

项目根目录的 `docker-compose.yml` 已定义好开发库（唯一数据库）。

```bash
# 项目根目录
docker compose up -d
```

启动的实例：

| 项 | 值 |
|:---|:---|
| 容器名 | `situation-platform-db` |
| 镜像 | `postgres:16` |
| 端口 | `5432`（映射到本机） |
| 数据库 | `situation_platform` |
| 用户名 | `situation` |
| 密码 | `situation_dev_password` |
| 默认连接串 | `postgresql+psycopg2://situation:situation_dev_password@127.0.0.1:5432/situation_platform` |
| 数据持久化 | 卷 `pgdata`（`/var/lib/postgresql/data`） |

验证启动成功：

```bash
docker compose ps          # STATUS 应为 Up（healthy）
docker ps | grep postgres  # 或在容器列表看到 situation-platform-db
```

生命周期：

```bash
docker compose down        # 停止，数据保留在卷中，下次 up -d 数据仍在
docker compose down -v     # 停止并清空全部数据（卷删除，慎用）
```

---

## 4. 方式 B：使用已有的 PostgreSQL 实例

若本机已有 PostgreSQL（或团队共用服务器），跳过 Docker，手动建库建用户即可：

```sql
-- 用超级用户执行（如 postgres）
CREATE USER situation WITH PASSWORD 'situation_dev_password';
CREATE DATABASE situation_platform OWNER situation;
GRANT ALL PRIVILEGES ON DATABASE situation_platform TO situation;
```

> 连接串里的用户名 / 密码 / 库名可以完全自定义，**只要与 `backend/app/.env` 的 `DATABASE_URL` 一致**即可（见第 5 节）。

---

## 5. 配置 `backend/app/.env`

### 5.1 文件位置与为什么必须创建

- 文件：`backend/app/.env`（**注意在 `backend/app/` 下，不是根目录**）
- 该文件已被 `.gitignore` 忽略，**clone 代码不会自带**，必须手动创建
- **为什么必须有**：后端 `backend/app/config.py` 在导入时用 `os.environ['LLM_BINDING_API_KEY']` 等**直接索引**构建配置，`.env` 缺失且系统环境变量里也没有这些键时，后端 import 会直接 `KeyError`，服务起不来
- `.env` 是**本地配置而非数据**：每个环境各自维护，不需要共享实际值

### 5.2 完整模板（可直接复制）

新建 `backend/app/.env`，内容如下（LLM 五项为占位值即可，本项目 PMWNB 流程不使用大模型）：

```ini
# ==================== LLM（占位，本项目不实际使用） ====================
LLM_BINDING_API_KEY=sk-placeholder
LLM_BINDING_HOST=http://127.0.0.1:8000
LLM_MODEL=placeholder-model
MAX_TOKENS=2048
MAX_ASYNC=4

# ==================== 数据库（PostgreSQL） ====================
# 方式 A（Docker，默认值）本地开发可整行省略，db.py 自动回落默认连接串：
#   postgresql+psycopg2://situation:situation_dev_password@127.0.0.1:5432/situation_platform
# 方式 B（自有实例）必须按实际填写：
# DATABASE_URL=postgresql+psycopg2://<user>:<password>@<host>:<port>/<dbname>
```

要点：

- **`DATABASE_URL` 是唯一与数据库相关的配置项**。用 Docker 默认实例时**可以整行不写**（`backend/app/db.py` 自带默认值）
- 若 `DATABASE_URL` 已写，则必须以它为准，与第 3 / 4 节的连接串保持完全一致
- 密码含特殊字符需 URL 编码，例如 `@` 写作 `%40`

## 6. 建表 + 写入基础数据（Alembic）

表结构通过 Alembic 迁移管理。执行（需在 `backend/` 目录，且数据库可连接）：

```bash
cd backend
python -m alembic upgrade head
```

这一步会：

1. 创建 **12 张业务表**
2. 写入基础 seed：**场景表**（网络攻击 / 电力停电 / 航母调度 / 地质灾害等）与**算法表**（PMWNB / A2WNB / MAWNB / EMAWNB / DIWNB，含 `param_schema`）

常用命令：

```bash
python -m alembic current          # 查看当前版本
python -m alembic history          # 查看迁移历史
python -m alembic downgrade -1     # 回退一步
python -m alembic upgrade head --sql   # 离线预览 SQL（无需数据库）
```

---

## 7. 注册测试数据（seed 脚本）

第 6 步建好了"骨架"（表 + 场景/算法），还需注册运行所需的测试数据。在**项目根目录**执行：

```bash
python scripts/seed_test_data.py --skip-copy
```

> `--skip-copy`：跳过从源目录拷贝 ARFF，直接登记 `data/` 下已有的文件。若没有现成 `data/` 而是另有源目录，去掉该参数并加 `--source <路径>`。

该脚本做三件事：

1. **测试账号**：`admin / admin123`（管理员）、`alice / alice123`（普通用户）
2. **数据集登记**：扫描 `data/` 下的 ARFF → 解析字段 → 写入 `datasets` 表（`file_path` 为相对路径 `data/<场景>/<文件>.arff`，并写入 `fields_schema`）
3. **风险阈值**：按场景写入 `risk_threshold` 表

脚本结束会打印各场景下已登记的数据集数量，用于核对。

## 9. 常见问题（FAQ）

| 现象 | 原因 / 解决 |
|:-----|:------------|
| `docker pull postgres:16` 卡住 / 超时 | 网络需代理/梯子，或配置 Docker 镜像加速 |
| `docker compose up` 后 `STATUS` 不是 healthy | 端口 5432 被占用（改 `docker-compose.yml` 端口映射，同时改 `.env` 的 `DATABASE_URL`） |
| `alembic upgrade head` 报连接失败 | 数据库没起 / `.env` 的 `DATABASE_URL` 不对（先 `docker compose ps` 确认） |
| 后端启动报 `KeyError: 'LLM_BINDING_API_KEY'` | `.env` 缺失或没保存（见第 5 节，文件必须在 `backend/app/` 下） |
| `seed_test_data.py` 提示"场景不存在" | 没先执行 `alembic upgrade head`（第 6 步），场景 seed 未写入 |
| 数据集没登记上 | `data/` 下没有对应 ARFF 文件，或路径与脚本 `SCENARIO_DIR / DATASETS` 配置不一致 |

## 补充：与数据文件（`data/`）的关系

- 数据库不存数据文件本身，只存**路径与字段描述**；训练/推理时后端按 `file_path` 去 `data/` 读 ARFF
- 因此"数据一致" = **`data/` 文件夹 + 上述第 6、7 步的数据库状态**
- 模型训练产物（`.model` 文件）保存在 `backend/storage/models/`，为可再生产物，重训即可再生成，不要求手动迁移
