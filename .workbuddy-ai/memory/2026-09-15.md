### 实测结论（在本机已运行的开发环境上只读测量）

- 已排除：响应体过大（实际 1.6~5.7KB，gzip 无意义）、DB 慢、Java 推理服务

### 根因

1. `dashboard_service.py:304` 的 `_DatasetReader` 缓存生命周期是「一次请求」，且在 `:495 / :666 / :745 / :1195` 每个请求都重新 new。
2. `dashboard_service.py:323` 的 `label_stats` 只需要标签一列的两个数字，却调 `read_arff(path, max_rows=None)`（`arff_reader.py:84`）把**所有列所有行**物化成 Python 字符串，`_split_data_row`（`arff_reader.py:53`）还是手写逐字符状态机。
3. 量化：全量解析 11 个 ARFF = 1.83s；只统计标签列（csv.reader / str.split）= 0.080s，**23x**。
4. 前端附带问题：`main.ts` 里 `bootstrap().finally(() => app.mount())` 导致首屏白屏等一个 `/auth/me`；`router/index.ts:6` 静态 import `RiskAnalysis` 未懒加载；Element Plus 全量引入（入口 chunk 979KB + CSS 381KB，dev 预构建 element-plus 1.9MB）。
5. 开发环境用 `npm run dev`，首次打开要拉约 3.5MB 未压缩依赖 JS。

## 性能优化第二轮（同日续做：画像热路径 + Element Plus 按需 + 静态站点修复）

### 1. 画像聚合热路径

cProfile 实测 `_network_profile` 单请求调 `_num` **16.7 万次**、`_clean` **23 万次**、`str.strip` **200 万次**。

改动：`_num()` 加快路径 —— 首尾字符都不在 `_QUOTES` 时直接 `float()`，失败再落回慢路径。

- **等价性**：195 万个真实单元格 + 70 个边界用例（nan/inf/Infinity/1_000/.5/12./区间串/引号/空白/缺失）逐个比对，**0 处不一致**
- 效果：`_num` 吞吐 1.14x；network 150→118ms、geological 121→102ms

**失败尝试（重要教训）**：给 `_clean()` 加「首尾无引号则跳过 strip」的快路径，实测**反而慢 0.85x** —— CPython 的 `str.strip()` 无需裁剪时原样返回，比额外的下标判断更便宜。已回退，回退后还更快（118ms vs 126ms）。**不要想当然地"优化" str.strip。**
