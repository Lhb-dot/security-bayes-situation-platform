## ⚠️ 项目级隐患：style.css 的 `.el-button` 暗色覆盖是**失效**的

`style.css:1231-1251` 写的 `.el-button { background: rgba(91,166,255,.1) }` 等规则**实际不生效** —— 与 Element Plus 自身样式**同权重**，而 EP 的样式表在 style.css **之后**加载，后写者胜。

实测证据：新弹窗里 `<el-button>取消</el-button>` 渲染成 **白底 `rgb(255,255,255)` + 深灰字**，`--el-button-bg-color` 仍是 EP 默认 `#fff`；primary 也是 EP 默认 `#409eff`。

**唯一有效写法**（`ReportCenter.vue` 就是这么绕过去的）：覆盖 EP 的 CSS 变量并加 `!important`：
```css
.xxx .el-button {
  --el-button-bg-color: rgba(91,166,255,.1) !important;
  --el-button-border-color: rgba(125,201,255,.3) !important;
  --el-button-text-color: #9ad6ff !important;
}
```
或直接对属性加 `!important`。我在 `.ai-setting-dialog .el-button` 里按后者处理。

**未修 style.css 本身**（影响全站 el-button，超出本次范围）。如果后续发现别的页面按钮也是白底，根因就在这里。

## 梳理：报告中心（ReportCenter）完整逻辑

全链路已通读：`views/Model/ReportCenter.vue`(1299行) → `api/reportApi.ts` → `endpoints/report_routes.py` → `services/report_service.py` → `services/report_nl.py` → `report` 表。

- 端点：GET `/reports`（列表）、GET `/reports/{id}`（详情）、POST `/reports`（手填 content，**前端未接入**）、POST `/reports/generate`（服务端自动组装，前端唯一使用）、PUT `/reports/{id}/schedule`、DELETE `/reports/{id}`。
- 三级权限隔离：SUPER_ADMIN 全平台/指定用户；SCENARIO_ADMIN 强制本人场景；SCENARIO_USER 在 generate 中 scope 被硬置 `self`。
- generate 五步：权限归一化 → `_gather_events`/`_gather_records` → `_build_report_data`（九段：report_info / overview / prediction / model_analysis / model_evaluations / feature_analysis / trend / key_events / data_notes）→ `report_nl` 产出 analysis_nl + guidance_nl → `_render_content` 渲染 Markdown 存 `content`，结构化数据存 `report_data`(JSONB)。
- NL 为纯规则模板 + 可选 vLLM 润色（失败一律回退模板），不依赖 AI 可用性。
- 隔离口径（`_gather_events` / `_gather_records` 两套**不同**过滤链，务必区分）：
  - **风险事件 RiskEvent**：`scenario_id` + 角色分支（超管：`JOIN dataset ON risk_event.dataset_id` 且 `dataset.visibility='platform'`；场景用户：`created_by_user_id=本人`；场景管理员：无额外过滤）+ `scope='user'` 时叠加 `created_by_user_id=目标用户`。
  - **推理记录 InferenceRecord ⋈ ModelVersion**：`model_version.scenario_id` + 角色分支（超管：`JOIN dataset ON model_version.dataset_id` 且 `visibility='platform'`；场景用户：`user_id=本人` **且** `model_version.status='PUBLISHED'`；场景管理员：无额外过滤）+ `scope='user'` 时叠加 `user_id=目标用户`。
- 三个反直觉点：① 超管被 `platform` 可见性卡住，**场景管理员反而能看本场景全量**（含 company/personal 数据集、含非 PUBLISHED 模型）；② 事件按"创建人"过滤、记录按"执行人"过滤，且记录多一层模型状态过滤；③ 超管的"全平台"在 UI 上**强制选一个场景**，实际是"单场景的全平台可见数据"，跨场景需直接调接口传 `scenario_id=null`。

## 答疑：数据集中心 11 个 vs 场景中心合计 9 个（口径差异，非 bug）

**根因：场景中心的「有效数据集数」做了同源去重** —— `dashboard_service.py` 的
`CARRIER_LOGICAL_IDS`（carrier_feature2_biaoqian / carrier_feature2_lisan / carrier_paired_trail）
经 `_group_key()` 全部映射为 `carrier_shared_source` 一组，`_effective_counts()` 按组计数并取
`CARRIER_CANONICAL`（biaoqian）为代表，故舰面调度 3 → 1，全局 11 − 2 = 9。
`docs/首页字段口径说明.md:116` 已写明「11 文件 − 2 同源衍生 = 9」。

分布：网络 2 + 电力 1 + 地质 5 + 舰面 3 = 11；场景中心 2 + 1 + 5 + 1 = 9。

**次要差异（当前未触发，但口径确实不同）**：
- 数据集中心 `DatasetService.get_list` 不过滤 `status`，且按**行**计数（同 logical_id 多版本各算一条）；
- 场景中心 `get_scenario_overview` 只取 `status=ACTIVE`，且按 logical_id 分组去重。
→ 一旦有数据集被停用或出现 v2，两个数字会进一步拉开。

**中文名来源**：`constants.py` 的 `DATASET_DISPLAY_NAMES`（logical_id → 中文名）+ `dataset_display_name()`
兜底返回 logical_id 本身。`DatasetService._to_dict` 是 `dataset.name or dataset_display_name(logical_id)`，
即 DB 列 `dataset.name`（迁移 `20260915_000002_add_dataset_name`，用户上传时自填，平台预置数据保持 NULL）优先。

### ★ 真正的根因：`row_to_dict` 的日期格式少了年份（全项目级 bug）

`backend/app/utils/common.py:85` 把所有 datetime 统一 `strftime("%m-%d %H:%M:%S")` —— **没有年份**，
所以接口下发的 `uploaded_at` 是 `"08-08 13:10:41"`（14 位），而前端多处按 `YYYY-MM-DD` 写：

| 前端位置 | 写法 | 旧格式下的结果 |
|---|---|---|
| `DatasetCenter.vue:432` | `.slice(0,10)` | `08-08 13:1` ← 用户看到的"被压缩" |
| `situationApi.ts:103,124` | `.slice(0,10)` / `day.slice(5)` | 按日聚合出垃圾日、label=`13:1` |
| `dashFormat.fmtDate` | `.slice(5)` | 语义错位（但调用方传的是 `date.isoformat()`，侥幸没坏） |
| `NetworkDashboard.vue:56` | `startsWith(todayStr())` | **"今日告警"恒为 0** |
| `AdminOverviewView.vue:99` / `ScenarioStatusCard.vue:58` | `new Date(x.replace(' ','T'))` | 解析失败 → 近 24h 统计错 |
| `NetworkDashboard.vue:102` | `.slice(0,16)` | 想取到分钟，14 位字符串下取了个寂寞 |

**判据：`%m-%d %H:%M:%S` 全项目只有这一处**，其余后端全是 `%Y-%m-%d`
（`main.py` 多处、`report_service.py:310` 的 `%Y-%m-%d %H:%M`、`_activity_trend` 的 `date.isoformat()`）。
→ 改回 `%Y-%m-%d %H:%M:%S` 并同步 docstring。**这一改顺手修掉上表后三行的真 bug。**
